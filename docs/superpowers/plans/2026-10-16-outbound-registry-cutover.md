# Opt-in outbound registry cutover — P2.3

Parent: [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24). First prerequisite: [#119](https://git.subcult.tv/subculture-collective/overlaid/issues/119), [atomic retained reply batches](../../runbooks/reply-batch-admission.md). This plan describes implementation boundaries; no startup sender is enabled by the plan or batch API.

## Current paths

| Path | Observed behavior | Integration requirement |
| --- | --- | --- |
| `Server.dispatchRetainedChat` → `EventsForNormalizedChat` → `publishEventSubContext` | One existing processor handles normalized input, including the general Chat command registry. A fenced dispatch receipt prevents handler replay. Custom chat responses reach `publishEventContext`, which currently sends directly with broadcaster credentials. | Carry the canonical retained source through this synchronous execution. Derive stable follow-up keys from command identity/revision and effect position; random display-event IDs must not become deduplication keys. Collect actual chat replies and admit their batch once. |
| `completeNewsroomRequest`, `newsroom_current` | The same registry checks command revision/role and synchronously selects the approved current item, then calls the central direct chat sender. Other Newsroom commands mutate retained editorial state. | Route the actual reply through the same source-bound admission collector. Preserve synchronous command validation and editorial ownership; do not add a parser or separate Newsroom settings. Batch chat admission alone does not make editorial mutations transactional with the action ledger. |
| Dashboard Newsroom current/raffle announcement | An authenticated POST constructs text and calls `sendTwitchChatMessage`; success currently means the provider call completed. It has no normalized chat source. | Add an explicit retained manual-source identity/idempotency and permission contract before durable cutover. Return truthful queued versus delivered receipts. Never fabricate a viewer chat event to satisfy the chat-source foreign key. |
| Generic `publishEventContext` / central `sendTwitchChatAction` | `chatResponse` data triggers the direct broadcaster transport. The `sendOutboundChatForEvent` helper has no repository callers beyond its definition. | Enforce the selected sender at the central boundary, including unbound callbacks. A retained-mode failure must not fall back to this transport. |
| `bot.TimerScheduler` | Current timer events produce overlay ticker/alert data and audit records, with no `chatResponse`; they do not call Twitch chat. | Preserve overlay-only behavior. Do not add a chat effect as part of migration. A future chat timer needs a versioned occurrence/source contract. |
| Built-in overlay commands and publication | Existing clear/BRB/ticker and display state effects share publication, but are not automatically chat replies. | Keep their current state/history/OBS behavior while collecting only explicit chat responses. |
| Moderation enforcement workflow | Publication invokes the existing moderation workflow separately from chat responses. | Inventory and fence each effect before selecting retained moderation. Chat batch admission cannot provide cross-kind atomicity or authorize moderation. |

The inventory is source evidence from this checkout, not proof of live provider behavior.

## Ordered implementation units

1. **Atomic source-bound reply batches — #119.** Preserve one-item identities, immutable conflicts, combined limits, exact source deadlines and one payload-free job per action. Fail the entire new batch on conflict/quota/enqueue failure. Tests cover duplicates, partial allowance, source/tenant isolation and lock-delayed expiry.
2. **Source-bound registry reply collection — #123.** The explicit [collector implementation](../../runbooks/registry-reply-collection.md) is merged in PR #124 and not selected at startup. [Transactional snapshot binding](../../runbooks/registry-admission-binding.md), merged in PR #126 under #125, holds saved commands through admission commit. [Saved command snapshot metadata](../../runbooks/registry-command-snapshots.md), tracked by #121, supplies the saved ID and tenant-scoped configuration/write fingerprint. Queued Newsroom requests compare the snapshot at a fresh registry read; the fingerprint alone is not an admission fence; the guarded batch supplies the transaction boundary for new replies. Add a private execution context/collector tied to the canonical retained event and current tenant. Use the existing registry once; preserve command revision, cooldown, plan, Newsroom and publication/cancellation behavior. Reject unbound/reordered/conflicting output identities. Test custom chat replies, Newsroom current, empty replies, duplicate dispatch and cancellation with no provider effects. Do not silently convert overlay events into chat messages.
3. **Non-chat source contracts — #127.** The [manual source/admission foundation](../../runbooks/manual-outbound-sources.md) is merged in PR #128 and supplies separate retained identities and atomic action/jobs. The [request/UI intent contract](../../runbooks/manual-announcement-intents.md), tracked by #129, adds preview/content locks, receipt-only retries and truthful queued acknowledgement. Retain manual request/permission/idempotency with bounded deadlines and deletion/export policy. Inventory timer/manual/moderation callers and add only the source contracts their actual effects require. Distinguish queued acknowledgements from delivery receipts; preserve explicit user action and no replay after uncertain effects.
4. **One durable sender selection/controller.** Extend the existing database controller ownership rather than adding a parallel dispatcher. Retain an explicit opt-in mode guard that old send paths cannot bypass. Validate separate execution, pacing and exact-kind worker roles/database identities before starting any client. Fail closed on controller loss, role drift or incompatible schema/state; never fall back to broadcaster sending. Keep defaults unchanged and selected-identity authorization fresh.
5. **Lifecycle, readiness and rollback.** Expose fixed readiness failures for required pools/controller/worker compatibility, with secret-free diagnostics. Bound startup/shutdown and detached bookkeeping. Cover restart, known echo IDs, shared identity revocation, reauthorization, pause/cooldown, canceled publication and removed sources. Stop workers before rollback and preserve all claims, uncertain outcomes, cooldowns and version-two fair state. Rollback must use a compatible build or leave retained sending stopped.
6. **Opt-in application integration and acceptance.** Wire only after the preceding compatibility fixtures pass for every active reply path. Run actual River mixed-load/deadline fixtures through the existing registry; record bounded capacity and expiry honestly. Real Twitch/OBS and bot/badge evidence remain separate controlled acceptance under #39/#40/#24.

## Verification and limits

Each code unit runs `GOTOOLCHAIN=go1.26.0 bash scripts/ci-postgres.sh` with disposable fixtures and mocked transports. The acceptance gate must prove that legacy and retained execution cannot both send, and that failure of retained admission or a controller cannot cause a legacy send. Source lifecycle, tenant isolation, delivery uncertainty and exact original deadlines stay enforced.

The conservative chat budget remains twenty attempts per thirty seconds; no capacity increase is implied. A thousand queued actions is not a thousand-channel delivery acceptance result. Provider registrations/credentials, a live deployment, production migration, actual Twitch messages and a named release require their own authorized controlled work and receipts.
