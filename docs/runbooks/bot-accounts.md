# Tenant-owned bot identity storage

[Issue #60](https://git.subcult.tv/subculture-collective/overlaid/issues/60) adds the persistence boundary for a tenant bringing its own Twitch bot. This is a store foundation: no bot OAuth route, desk control or sender switch is enabled. Existing broadcaster authorization, EventSub, commands and Newsroom continue through their current paths. The [service-owned vault](service-bot-vault.md) supplies a separate administrative access boundary; tenant delegation and OAuth remain later units.

Apply `0010_bot_accounts.sql` with administrator migration credentials before starting this revision in managed mode. It creates a forced-RLS table and adds a nullable composite tenant/bot reference to broadcaster connections. Existing connections remain unbound. File mode has no new persistence path. No credentials are copied or imported automatically.

`SaveValidatedBotAccount` accepts a version 1 internal credential envelope after the trusted OAuth adapter has validated the Twitch client and subject. Access and refresh tokens must be present and bounded; expiry must be in the future. The store normalizes login/scopes and caps retained accounts at eight per tenant, including revoked identities. This is a storage safety bound, not a commercial plan allowance. Saving the same provider subject updates its existing identity; saving or reauthorizing it clears its binding.

Bot ciphertext uses the existing versioned AES-GCM keyring, authenticated to tenant, bot ID, provider and key version. It is separate from broadcaster ciphertext. `BotAccount` metadata and owner exports allowlist identity, scopes and revocation state; credentials, ciphertext and key versions are excluded. Audit rows contain fixed action/provider fields only.

Save, bind and revoke require the current tenant owner. Binding also requires an active broadcaster connection with the expected provider subject and an active bot in the same tenant. Composite foreign keys reject cross-tenant references independently of store predicates and RLS. Broadcaster reauthorization or revocation clears its binding; reconnecting a channel never inherits one.

`ResolveBoundBotAccount` is an internal trusted-dispatch API, not a browser route. Callers must check the effect's capabilities, grants, bot role and current tenant permissions before sending. Binding alone grants no send or moderation permission. Resolution requires the expected broadcaster subject and bot ID, rechecks active state, and serializes refresh under tenant/connection/account locks. Provider callbacks must use the supplied context and bounded network timeouts. They must validate client/subject again; changing the bot subject, returning expired credentials, malformed data or an error rolls back the transaction. Successful resolution re-encrypts with the active key version. Keep old keys until all retained credentials have been rotated and independently verified.

Revocation atomically clears tokens, key version, scopes and bindings. Tenant deletion cascades the bot rows. Revoked account metadata remains until tenant deletion; viewer deletion does not revoke an authorized bot identity. The lock order is tenant, connection, account, including broadcaster vault operations, so concurrent refresh and revocation cannot resurrect a revoked identity. A token already returned to trusted code cannot be recalled; future outbound execution must revalidate and record ambiguous provider delivery through its own receipt boundary.

For rollback, stop the managed revision before starting an older binary. Preserve the database and keyring backup. Existing broadcaster credentials remain usable by the previous sender. Older binaries ignore bot bindings; they must not perform connection reauthorization while a newer bot consumer is active. Leave the additive table/column in place during rollback, and retain ciphertext with its matching keys. Destructive schema removal is a separate operator action.

Local qualification uses the disposable PostgreSQL harness: tenant/owner isolation, forged references, independent ciphertext, redacted export, refresh serialization and rollback, restart/key rotation, admission bounds, revocation, reconnect and tenant deletion. These fixtures use synthetic credentials and make no provider requests. They do not qualify live OAuth, bot moderator status or Twitch delivery.
