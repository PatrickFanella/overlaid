# Opt-in retained Twitch chat sender

Tracking: [#133](https://git.subcult.tv/subculture-collective/overlaid/issues/133), parent [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24). This selects the existing source-bound registry collector, manual announcement contract, durable executor and restricted outbound worker through the existing managed chat controller. The default is `TWITCH_CHAT_SEND_MODE=legacy`. Adding this code does not configure or deploy a live installation.

## Configuration and ownership

| Setting | Required value or boundary |
| --- | --- |
| `TWITCH_CHAT_SEND_MODE` | `retained` explicitly selects durable chat sending; `legacy` remains the default. |
| `TWITCH_CHAT_DISPATCH_MODE` | Must be `retained` when retained sending is selected. File mode is rejected. |
| `DATABASE_URL` | Existing non-owner product/tenant login, with current migrations through 0026. |
| `PLATFORM_WORKER_DATABASE_URL` | Separate retained-ingestion login with only the chat-dispatch queue role. |
| `PLATFORM_OUTBOUND_WORKER_DATABASE_URL` | Separate login inheriting only the outbound chat worker role. It must not also reach product, moderation, pacing or vault privileges. |
| `OVERLAID_PACING_DATABASE_URL` | Separate restricted chat pacing login. This is the same private setting used by the read-only pacing probe. |
| `OVERLAID_BOT_EXECUTION_DATABASE_URL` | Optional separate restricted shared-bot execution login. Without it, selected shared identities fail closed. Never supply the service administrator DSN. |
| Existing Twitch client and vault settings | Required for the selected authorization adapter. Credentials remain private and vault encrypted. |

All pools must identify the same database, server and schema. Constructors validate reachable roles, including `NOINHERIT`/`SET ROLE` membership, exact queue policies, forced RLS and fair-sequence compatibility before either client starts. Product credentials may read the existing published-only bot catalogue; they cannot reach private service-vault, global pacing or worker policies. Private column grants invalidate queue/pacing isolation as well as table grants. Optional shared custody requires its restricted role and matching database identity.

A read-only startup scan validates bounded retained pacing account/turn formats. It creates, prunes, repairs and reserves nothing. An incompatible format fails startup; version-two turns, charged attempts, cooldowns and claims remain intact. The existing executor still validates the selected account state before acquiring a permit.

Every managed writer uses the [same controller lease](retained-twitch-chat.md), including EventSub-disabled manual writers. A competing application fails startup. Preparation has a ten-second controller budget; worker startup has a separate ten-second budget. Both clients have a leasing gate: neither may consume a job until both have started successfully. Failed preparation leaves jobs and dispatch receipts unstarted. A successful startup installs the retained collector in every runtime before that runtime starts its background work.

## Effects and receipts

The existing general Chat registry remains the only command manager and parser. Custom chat/both replies and synchronous Newsroom current replies collect actual output, then commit a source-bound batch once. Overlay-only timers and display effects keep their existing behavior. Unbound chat callbacks are rejected by the selected central sender. Retained admission or execution failure never calls the legacy broadcaster transport.

Manual Newsroom current/raffle requests use [preview fingerprints and saved browser intents](manual-announcement-intents.md). Their explicit manual sources and action/jobs commit together. An acknowledgement reports queued/running work separately from delivery; receipt-only retries cannot recreate a missing source or repeat an uncertain request. Switching modes does not reinterpret an existing unresolved intent.

The existing Twitch adapter resolves the selected broadcaster, own bot or explicitly consented/published shared bot with fresh scope, subject, role, binding and plan checks. The controller wrapper rechecks ownership and pool compatibility before authorization and immediately before the adapter's one bounded send. Authorization and transport inherit application cancellation. The executor keeps its original deadlines, non-replayable claims, detached completion, successful echo IDs and global conservative budget of twenty attempts per thirty seconds with one-second channel spacing. No higher provider capacity is implied.

The controlled executor also holds the tenant's send/echo gate from before the ledger claim through provider outcome, durable successful message-ID storage and ledger completion. Queued echoes wait at the same gate before command processing. Runtime and in-flight references preserve that gate across invalidation; the original attempt is canceled, while a confirmed late response can still store its ID before a rebuilt consumer proceeds. Entries disappear when no runtime or attempt owns them. Gate waits stay inside the existing attempt deadline and occur before a claim; failure preserves charged pacing/turns and never grants provider replay.

Only chat sending is selected here. Moderation workers and app-token/conduit transport remain unregistered. Existing moderation/editorial/history/display effects are separate boundaries; a chat batch does not make them transactional with delivery. User-token sending does not establish a Chat Bot badge.

## Readiness, shutdown and rollback

`/readyz` adds the fixed `chat_outbound` check when selected. It reports whether both started clients and controller remain available. The controller heartbeat rechecks pool roles/policies, and authorization/transport perform their own fresh checks. Observed controller or pool failure cancels effects and degrades readiness without switching senders. A clear readiness report is not proof of a provider grant or successful delivery. `/healthz` remains process liveness.

Ownership queries serialize their complete query/row-scan pair on the pinned advisory-lock connection, including shutdown's unlock query. Waiting for that connection stays inside the one-second ownership-check budget and honors caller cancellation. A canceled caller does not stop other tenants; an expired check budget fails closed. This prevents overlapping heartbeat and effect checks from corrupting the driver's active result.

Retained ingestion prepares the tenant runtime before writing a new handler-start receipt, for both legacy and retained sending. The explicit `platformdispatch.NewPreparedClient` callback binds the exact runtime to the eventual handler; it executes no command and grants no provider permission. Preparation failure uses the existing three-attempt pre-handler retry path without a receipt. Missing or expired sources and existing completed/running receipts keep their terminal/no-replay path. Locked source reconstruction refuses a new start if no runtime was prepared, including a source/receipt change between the preliminary metadata read and the fence. Runtime invalidation cancels the prepared handler instead of making it acquire a replacement after the fence.

The loaded-runtime limit defaults to 100. Explicit `TENANT_RUNTIME_LIMIT` values from 1 through 1000 select a deployment bound after restart, with no idle eviction or automatic capacity increase; see [runtime capacity](runtime-capacity.md). An observed capacity denial adds the fixed `tenant_runtimes=degraded` readiness result. Releasing a slot or successfully preparing the waiting runtime clears that pressure result; this check does not establish health for every inactive tenant. Existing runtimes keep working. Retry exhaustion can leave an unexecuted source without a handler receipt; freeing capacity does not resurrect a discarded job or authorize a replay automatically.

Shutdown closes admission/leasing, cancels active effects, and stops both clients within one shared fifty-second budget before closing their pools or releasing controller ownership. Existing detached bookkeeping keeps its own bounded writes. Losing a provider response or completion write can leave an uncertain action; shutdown and restart do not authorize replay.

Startup persists `chat_send_mode=retained-v1` in the bootstrap tenant's `app_metadata` together with the retained dispatch guard. Any subsequent legacy-sender start on this revision is refused, including retained ingestion paired with legacy sending. Unknown sender guard versions also fail closed. The guard is installation-level state, not a tenant/browser control.

For rollback, stop all chat writers and retain action/source/job rows, dispatch receipts, echo markers, claims, uncertain outcomes, charged pacing attempts, cooldowns and fair state. Use a compatible build with retained sending or leave chat stopped. Earlier binaries do not honor the sender guard; they must not be started as a shortcut. Do not clear the guard, reset pacing state or discard receipts to enable replay. A deliberate redesign of the mode transition requires its own reviewed operational procedure and matched private checkpoints.

## Verification and remaining acceptance

Run `GOTOOLCHAIN=go1.26.0 bash scripts/ci-postgres.sh`. Disposable fixtures use real River leasing and synthetic provider responses. Startup rejects missing/mixed/foreign roles, missing adapter configuration and incompatible pacing state before work starts. Registry/manual delivery, duplicates, queued acknowledgements, receipt-only retries, durable echoes including an event injected during a blocked provider response and after runtime invalidation, manual broadcaster commands, restart-preserved pacing, role drift, readiness and sender downgrade rejection are qualified separately from live provider behavior.

The [#135 lifecycle fixtures](https://git.subcult.tv/subculture-collective/overlaid/issues/135) hold the real outbound worker after its first authorization and pacing permit, before its ledger claim. Revoking the broadcaster connection prevents a claim; reauthorizing the same subject makes the post-claim binding check reject the reply. Removing the retained source cascades its private action and prevents transport. Each case waits for permit completion and checks that its charged attempt remains. These changes happen before the claim; the fixtures do not establish cancellation of an already-started provider request.

The general registry fixtures also retain an input, disable its command before dispatch, and verify no reply is admitted. After enabling the command, one reply is delivered and the next input within its cooldown produces no additional action. Pausing a command does not retract an already-admitted reply snapshot. These fixtures use the existing registry and its normal command-cache refresh; they do not establish cooldown persistence across runtime replacement.

The [#137 selected-identity fixtures](https://git.subcult.tv/subculture-collective/overlaid/issues/137) extend that same application/River boundary to own and shared bots. Both delivery cases verify the selected bot subject and channel, its credential at transport, a running ledger claim, fresh authorization and moderator checks on both sides of the claim, and durable echo bookkeeping. Own-bot revocation/reauthorization and independent shared-consent revocation, unpublishing, service-grant revocation and service-credential reauthorization all reject delivery after the claim without broadcaster fallback. Each mutation happens after the first authorization/pacing permit and before the claim; the charged pacing attempt remains. Shared fixtures use the separate administrator pool only for setup/mutation and the configured execution pool for application custody.

The [#139 two-tenant fixture](https://git.subcult.tv/subculture-collective/overlaid/issues/139) mixes a provider quota rejection and cooled-down aged reply with another sender's fresh reply, duplicate input and overlay-only counter commands. The other tenant progresses before the aged reply's original deadline; the aged reply expires without a claim or extra transport. Both jobs and ledger rows become terminal, the original timestamp remains unchanged, and denied pacing adds no charged attempt or in-flight permit. This exposed a subsecond gap between whole-second job cancellation and precise ledger expiry, repaired by [pending-only worker expiry bookkeeping](outbound-worker.md).

The [#141 capacity fixture](https://git.subcult.tv/subculture-collective/overlaid/issues/141) fills a synthetic 100-entry runtime map and uses a real River job in both retained-ingestion modes. It reproduces the former failed-handler fence, then verifies receipt-free preparation failure, degraded readiness, one execution after releasing a slot, and cleared pressure. The fixture explicitly promotes the existing retry as the maintenance scheduler would; it does not measure natural retry timing or run 100 channel runtimes. Worker fixtures retain completed/prior-start/expired/missing-source behavior, and a prepared runtime rejects another tenant or invalidation without recreating resources.

Broader load acceptance remains under #24. These bounded fixtures do not establish thousand-channel capacity, continuous hostile-load fairness or application-level moderation priority. Identity fixtures do not establish provider-side revocation timing, a live moderator grant or cancellation of a provider request already in progress. The [#143 actual-runtime fixtures](runtime-capacity.md) qualify configured bounds of 100 and 1000 for runtime construction, retained overlay-only commands, isolation, overflow handling and ownership reacquisition. The #145 fixture also qualifies normal global resumption and populated restart for exactly 1000 tenants, with the initial sweep applying mixed retention policies to retained chat input and its cascades. Live connection, delivery/pacing, other retained data types and natural periodic-sweep load remain separate qualification. Controlled Twitch/OBS work under #39/#40, OAuth/bot badge evidence and production deployment remain separate gates. No live messages, credentials, provider registrations or production migration are performed by the fixture suite.

## Shared cooldown across tenant bindings and restart

[Issue #147](https://git.subcult.tv/subculture-collective/overlaid/issues/147) adds `TestRetainedSharedSenderCooldownAcrossTenantsAndRestart`. Two separately owned tenants explicitly consent to the same published shared bot for different broadcaster channels. A third tenant uses its own broadcaster identity. The real application sender, restricted shared execution pool, authorization callbacks, ledger, River worker and pacing store remain in the path; all provider responses are mocked.

A quota response in the first shared channel commits a 60-second account cooldown. The second tenant must complete fresh authorization and reach a durable pre-claim snooze for that same shared sender, without making a provider send. The unrelated broadcaster completes its reply while the shared sender is blocked. Closing and reconstructing the application must preserve the exact cooldown, pending action ID, River job ID and original source-derived deadline. The fixture observes natural job scheduling until that deadline expires; it does not clear pacing state, advance a clock or promote a retry.

The second action must expire without a claim or another pacing charge. The first provider attempt must stay terminal without replay; the unrelated delivery retains the sole successful echo marker in its own tenant. All dispatch receipts and queue jobs must settle, and pacing permits must be released. The fixture checks exact OAuth subjects, broadcaster role lookup, selected transport credentials and a running ledger claim before each mocked send.

This covers a finite three-tenant shared-cooldown/restart case. It does not establish natural sending after the cooldown window, shared-account saturation throughput, continuous-load fairness, moderation priority or live provider behavior. Broader load acceptance remains under #24.
