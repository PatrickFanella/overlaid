# Durable chat pacing

`internal/chatpacing` is the pacing foundation used by the [fenced outbound executor](outbound-executor.md). It has no provider client or browser route. [Retained chat startup](retained-chat-sender.md) opens its separate restricted pool only when explicitly selected; default broadcaster replies retain their direct path.

Apply `migrations/0015_chat_pacing.sql` and additive `0024_chat_permit_turns.sql` through the administrator migration workflow. It creates the `overlaid_pacer` NOLOGIN group and two forced-RLS tables. A separately provisioned login may inherit that group. `chatpacing.Open` requires an explicit DSN and validates current, original session and reachable roles, including NOINHERIT memberships. It rejects administrative privileges, schema creation, table ownership, access to other application tables and TRUNCATE/REFERENCES/TRIGGER on pacing tables. Each pacing table must retain its sole permissive role-scoped true/true policy, forced RLS and required DML grants. See the [shared pacing-role contract](pacing-role-validation.md) for construction checks and limits. Tenant runtime, chat worker and bot administrator roles receive no pacing access. Provision its separate login through the controlled deployment process before selecting retained sending. The controller revalidates metadata during execution and scans compatible retained state read-only at startup.

Budgets belong to the Twitch sender across every tenant using the canonical pacing database. The account key hashes the provider and sender ID; the channel key hashes provider, sender and channel ID. Rows contain only those hashes, bounded attempt timestamps, cooldowns and a hashed permit fence. They retain no raw tenant/action identity, message, credential, raw Twitch ID or plaintext permit token. [Fair admission](chat-permit-fairness.md) also retains bounded tenant/action hashes and original deadlines. Other applications using the same Twitch identity consume provider budget outside this store's observation.

The initial policy allows 20 attempted sends per rolling 30 seconds and at least one second between sends to the same channel. It applies the conservative account budget to every sender, without moderator, broadcaster or verified-bot boosts. Twitch documents its [shared per-user chat budgets and channel limits](https://dev.twitch.tv/docs/chat/#rate-limits); provider capability and role checks remain separate work.

`Acquire` atomically checks the account window, channel spacing, provider cooldown and in-flight lease using the database clock after locks. A granted permit charges a slot and retains a 30-second account lease. Different channels and different tenant callers using that sender share the lease and budget. A denied call returns the next known retry time without booking a future slot; an active lease may complete earlier than that time. The explicit executor uses [durable tenant turns](chat-permit-fairness.md) through `AcquireFair`; legacy `Acquire` rejects accounts in fair mode. This store does not implement moderation priority or reserve future slots for chatter.

The executor uses a conservative local permit deadline measured from acquisition start and reserves bookkeeping time. It must use a permit immediately, bound the provider attempt to ten seconds and complete all bookkeeping within its 30-second lease. `Complete` charges the slot at completion as well as start, keeps channel spacing from completion, and never refunds failed or canceled attempts. Provider retry-after applies conservatively to the entire sender. Completion uses a detached five-second transaction so cancellation cannot discard a cooldown. Very large valid delays remain future timestamps instead of overflowing. A replacement lease rejects the old permit's completion; a database failure leaves the current lease in place. The outbound action ledger separately governs delivery uncertainty and no replay.

Short database-only transactions use one schema-specific admission lock to serialize capacity, pruning and permit updates. No transaction or pool connection remains held during provider calls. Stored accounts are capped at 1,024 and channel pairs at 10,000; capacity exhaustion returns an explicit error. Inactive state older than one day is pruned on acquisition, while future account cooldowns and live leases protect their accounts. Tenant deletion does not reset shared budgets, and pacing state is excluded from tenant exports.

Run `bash scripts/ci-postgres.sh` for the required repository checks and uncached race suites. Fixtures cover concurrent acquisition, restart, cross-channel/shared-sender isolation, independent senders, forged/stale completion, cancellation, crash lease expiry, account exhaustion, pruning, capacity and role rejection. The pure state simulation sends no messages: 1,000 distinct channels take 24 minutes 30 seconds under this conservative account budget. It verifies pacing boundaries, not that a simultaneous 1,000-message burst meets the ledger's two-minute action deadline. The future executor must expire work that cannot fit its original deadline.

The migration is additive and has no backfill. Current application rollback can retain these unused tables. Before later executor activation, identify one canonical pacing database and validate its restricted role and product database identity. Once sending is active, preserve its pacing rows across restart and rollback; never clear them to bypass provider limits. Live Twitch behavior and distributed executor throughput remain unverified by these fixtures.

The [read-only inspection helper and operator probe](pacing-inspection.md) expose fixed headroom, blocking and original-deadline signals through an explicit restricted connection. They use the same timing policy and never create state or reserve a slot. Inspection is separate from priority scheduling, continuous alert delivery and application activation.
