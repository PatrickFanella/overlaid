# Tenant turns at moderation permit admission

Tracking: [#115](https://git.subcult.tv/subculture-collective/overlaid/issues/115), part of P2.2 under [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24), following merged [chat permit turns](chat-permit-fairness.md).

Moderation requires both a client/moderator sender permit and a client/broadcaster channel permit. Different moderators can contend for the same channel. `moderationpacing.AcquireFair` uses one bounded turn list per client and selects only actions whose two resource rows are eligible. Separate sender/channel turn lists could elect incompatible winners; one list orders the eligible actions without holding a provider connection or requiring independent resource pairs to wait for each other's completion.

Migration `0025_moderation_permit_turns.sql` adds the `client` bucket kind and a default-empty `fair_state` JSONB column to the existing restricted table. Only client rows may contain non-empty fair state, bounded to 256 KiB. Sender/channel leases, one-second spacing, cooldowns, forced RLS and role grants retain their existing contracts. The constructor requires the non-null JSONB column. No pool or worker is registered at startup, and this task does not apply a production migration.

There are at most 1,024 client rows, in addition to the existing 1,024 sender and 10,000 channel bounds. Each client retains at most 256 action entries and 128 tenant entries. Waiting actions bind context-separated tenant/action hashes to the exact sender:channel hash pair and original deadline. No raw tenant, action, client, moderator, broadcaster, credential, reason or message data enters these rows. Inactive client rows use the existing one-day pruning rule after all two-minute turn/action history is inactive.

The shared `internal/permitturns` codec preserves chat's version-one field names and hash keys. A moderation resource binding uses two lower-case hexadecimal hashes separated by a colon; chat retains its single channel hash. The shared decoder validates bounded arrays, version, field names, hashes, references, tickets and counter range. The database keeps chat's 128 KiB envelope and moderation's 256 KiB envelope. A full paired-resource fixture verifies the larger envelope at both array limits.

Under the existing short moderation admission lock, registration preserves an action's exact resource binding and future original deadline, at most two minutes ahead of the database clock. Selection considers both resources' spacing and live leases. The oldest tenant grant turn wins, with its earliest eligible ticket as tie breaker; new tenants enter at the current counter. A successful transaction retains the granted marker and updated turn with both charged resource fences. A denial registers metadata without reserving future spacing or a lease and returns a poll hint no later than one second or the original deadline. Missing resource rows are not eligible.

Independent pairs under one client can hold simultaneous permits. Different clients remain independent. Shared resources still admit one live permit, even when different moderators or independent pools contend. The explicit moderation executor uses its freshly authorized ClientID/ModeratorID and canonical ledger identity/deadline, then preserves post-claim identity, consent and binding checks before one bounded transport attempt. No chat completion validator or chat echo receipt is used.

Granted markers remain through their original deadlines. Duplicate callers cannot obtain another permit after normal completion. A pre-claim storage failure uses detached `CompleteUnclaimed`: only the exact current sender and channel fences permit removal of that action marker, while spacing and the tenant turn remain charged. A retry reconstructs the ledger; committed or uncertain claims remain non-replayable. Stale, forged or partially replaced permits cannot clear the marker or either resource fence. Normal completion, including rejection/uncertainty, retains the marker.

Legacy `Acquire` rejects a client once fair state is present. Stop older explicit clients before transition because older binaries ignore the new state column. Preserve additive schema, cooldowns, claims and uncertain outcomes on rollback; stop fair clients before rolling back application code. Do not clear fair state or pacing rows to bypass admission. The shared codec extraction does not change existing chat persistence or read-only inspection behavior.

This is fairness among registered work with eligible resources and callers that retry. A selected caller that disappears can delay other eligible work until its original deadline. Bounded capacity can reject additional clients, tenants or actions. The implementation does not prove service under unlimited hostile arrivals, account for every Helix consumer or qualify the full 1,000-channel phase target. Deterministic broader admission/qualification and opt-in registry cutover remain before activation.

Run `GOTOOLCHAIN=go1.26.0 bash scripts/ci-postgres.sh` for make verify and both uncached race suites. Disposable fixtures cover alternating tenant grants across different moderators sharing a channel, duplicate contenders through restarted pools, independent pairs/clients, no future reservations on denial, immutable resources/deadlines, blocked cancellation, expired selected callers, client/tenant capacity, malformed state, migration readiness, atomic grant rollback and detached fenced pre-claim cleanup. An executor fixture injects a claim failure, verifies zero provider callbacks, then one successful retry and no replay. Existing chat fixtures run against the extracted codec. Synthetic time edits isolate spacing/expiry; they do not measure natural throughput. No fixture sends a live provider message or changes production grants.
