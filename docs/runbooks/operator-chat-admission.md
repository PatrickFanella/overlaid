# Atomic operator chat-plan admission

[Issue #317](https://git.subcult.tv/subculture-collective/overlaid/issues/317) connects the [retained source plans](operator-chat-effect-sources.md) to the existing outbound ledger. `AutomationStore.AdmitOperatorChatPlan(ctx, actor, request, digest)` is an explicit managed-store operation. There is no HTTP, dashboard or startup caller. A future caller must bind authenticated account/workspace, controller ownership, live runtime and unresolved-request recovery before enabling it.

The caller supplies the original operator request UUID and exact reviewed plan digest. It cannot supply message text, effect IDs, target, variables, version, clock or deadline. Admission rechecks configure permission under the tenant lock, validates source and admission schema/roles, and regenerates the entire original canonical plan. Private input remains clock-only syntax2; no provider or random capture is invented.

New admission requires the original version still selected, the original Twitch channel still active, and sufficient combined chat/moderation stored-action allowance, capped at 10,000. A complete plan contains 1–16 text-only effects. Database time is observed after tenant, plan and connection locks; the original source deadline is never renewed. The admission record, every action and every payload-free `ChatSendArgs` job commit together. Failure returns no partial result and rolls back the whole batch.

Each ledger ID and action key is the source plan's stable traversal effect ID. `engine_source_id` binds the ledger to the exact source, connection and deadline through a composite cascading foreign key. Event and Newsroom identities remain unchanged. A source plan has its own source kind; it is never fabricated as viewer chat or a Newsroom announcement.

An existing admission resolves before current-pointer, connection, allowance and expiry checks, but still requires fresh permission, exact reviewed digest, canonical source validation and every original ledger payload. It returns fixed source/action IDs, original deadline and admission time with `Created=false`. This grants no replay, new job, claim or provider permission. Missing actions under the surviving admission marker refuse as purged; mismatched payloads refuse as conflict. Deleted jobs are never re-enqueued. A missing private plan cannot be reconstructed by admission.

The existing outbound worker/executor handles these actions. Fresh provider authorization, pacing, one-use claims, uncertain-outcome terminalization, successful echo markers and shutdown gates remain in force. Queue admission does not promise delivery or ordering among effects. The new store operation does not select a worker, open a pool or bypass the retained-send opt-in.

## Read-only original outcome recovery

[Issue #319](https://git.subcult.tv/subculture-collective/overlaid/issues/319) adds `AutomationStore.LookupOperatorChatAdmission(ctx, actor, request, digest)`. This explicit managed-store read resolves only the initiating actor's original request and exact reviewed plan digest. It repeats source/admission role and schema validation, fresh configure permission and tenant/lifecycle read fences, then regenerates the complete original canonical plan. It requires no active sender, controller or current selected version, and still works after deadline expiry, target revocation or allowance reduction while the private source remains retained.

The result contains source/run/digest, original deadline/admission time and 1–16 action summaries in original traversal order. Summaries expose only action ID, sequence, fixed state/code/failure and retry duration. Message text, target, provider message ID, payload/claim hashes, credentials and raw provider diagnostics are excluded. The admission time must fall within the original prepared-plan/deadline interval. One SQL statement snapshots all mutable action outcomes without taking execution row locks; private payload comparisons remain inside that query.

Every original action must match the canonical source, text, payload hash, capability, key, target and deadline. Missing, extra, mismatched or contradictory rows refuse the whole result; no partial prefix is returned. Known pending/running/delivered/rejected/uncertain combinations and fixed failure vocabulary are checked before projection. A pending record can remain pending after expiry: lookup does not terminalize it or infer delivery. Retry metadata describes the retained outcome and grants no scheduling or replay permission.

Prepared-but-unadmitted and missing private input return the existing fixed missing result. Deleted actions under a surviving admission marker return purged. Neither outcome proves a prior request failed or authorizes a replacement UUID. Lookup never admits, repairs, extends a deadline, reserves allowance/pacing, claims, re-enqueues, calls a provider or writes audit/trace data. No HTTP, dashboard or startup consumer is selected in this unit; those callers still need owned admission, scoped unresolved-intent handling and fixed transport projection.

## Migration and lifecycle

Apply `0044_operator_chat_admission.sql` before starting this binary. Stop older application writers and queue consumers before migration. The migration adds nullable `engine_source_id`, exact-one-of-three source validation, original-target/deadline cascading references, text-only engine shape and a source/effect unique index. Existing actions, jobs, claims, deadlines and receipts are preserved. Replacing the old source-check constraint name intentionally makes older runtime startup refuse the new contract. Already-running older processes must be stopped; a startup guard cannot invalidate their pools.

`engine_operator_chat_admissions` is forced-RLS metadata with tenant-runtime SELECT/INSERT only. Its immutable primary key references the original source-plan marker. Queue, pacing and credential roles receive no access. Admission repeats exact column, role, policy and validated nondeferrable constraint checks. Runtime startup requires forced RLS and the exact outbound source/target/deadline contracts.

Deleting the private plan through run/member/connection/retention lifecycle cascades its ledger actions and their jobs. The admission record survives with the original occurrence's plan marker, preventing recreation after private deletion. Tenant/occurrence deletion removes both metadata markers. Metadata-only exports and receipts include the engine source ID; private effect text, source bodies and raw request keys remain excluded. Admission records are bounded by the existing 10,000 source-plan markers and contain no viewer capture.

Rollback must preserve admission and source markers, ledger claims and jobs. Stop the new admission caller/consumers first. Older binaries deliberately fail startup against this schema; use a compatible runtime with engine admission disabled. Reverting the source constraint or deleting engine rows to force an older binary to start is not a safe rollback. This change has not been deployed or qualified against a real provider.

## Verification

Run `GOTOOLCHAIN=go1.26.0 make verify` and `GOTOOLCHAIN=go1.26.0 bash scripts/ci-postgres.sh`. Disposable PostgreSQL tests cover concurrent duplicates, exact digest binding, enqueue rollback, stale selection/target/permission/limit refusal, corruption and schema drift, original deadline after tenant-lock waits, metadata exports, immutable marker/queue-role isolation, lifecycle cascades and migration preservation. The existing executor fixture uses a simulated sender and verifies one delivery attempt across repeated calls. These checks do not prove real Twitch delivery, deployment or power-loss durability.

The first hosted run on `28e7013` passed standard HTTP tests in 553.777s, then hit Go's default ten-minute package watchdog during the race pass. The active stream refusal subtest had run for two seconds and was constructing its fixture; no assertion or race-detector failure preceded the timeout. The same local race package passed in 566.984s. Application tests now have an explicit 15-minute package budget, with a 35-minute hosted job budget for both passes and setup. Individual request, database and worker deadlines remain unchanged. A new hosted pass is still required before merge.
