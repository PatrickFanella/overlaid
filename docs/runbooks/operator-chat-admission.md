# Atomic operator chat-plan admission

[Issue #317](https://git.subcult.tv/subculture-collective/overlaid/issues/317) connects the [retained source plans](operator-chat-effect-sources.md) to the existing outbound ledger. `AutomationStore.AdmitOperatorChatPlan(ctx, actor, request, digest)` is an explicit managed-store operation. Account delivery transport is described below; dashboard and automatic startup admission remain unselected. A future caller must bind authenticated account/workspace, controller ownership, live runtime and unresolved-request recovery before enabling it.

The caller supplies the original operator request UUID and exact reviewed plan digest. It cannot supply message text, effect IDs, target, variables, version, clock or deadline. Admission rechecks configure permission under the tenant lock, validates source and admission schema/roles, and regenerates the entire original canonical plan. Private input remains clock-only syntax2; no provider or random capture is invented.

New admission requires the original version still selected, the original Twitch channel still active, and sufficient combined chat/moderation stored-action allowance, capped at 10,000. A complete plan contains 1–16 text-only effects. Database time is observed after tenant, plan and connection locks; the original source deadline is never renewed. The admission record, every action and every payload-free `ChatSendArgs` job commit together. Failure returns no partial result and rolls back the whole batch.

Each ledger ID and action key is the source plan's stable traversal effect ID. `engine_source_id` binds the ledger to the exact source and connection through a composite cascading foreign key (`platform_outbound_engine_source_v2`, migration 0045). Each engine action also stores its own fixed window: `not_before` is the occurrence clock plus the reply's `delayMs`, and `deadline` is the plan deadline plus the same offset. Immediate replies keep offset zero, so their window matches the plan. A CHECK requires `not_before` before the deadline on engine rows and forbids it on chat and Newsroom rows. Queueing schedules a delayed reply's job at `not_before`; the executor defers it before pacing, authorization or any claim, and `Start` refuses a claim before that time without changing the row. Admission of a delayed plan still must happen before the plan deadline. Delayed jobs depend on River promoting scheduled jobs to available, the same path snoozes and retries already use. Event and Newsroom identities remain unchanged. A source plan has its own source kind; it is never fabricated as viewer chat or a Newsroom announcement.

An existing admission resolves before current-pointer, connection, allowance and expiry checks, but still requires fresh permission, exact reviewed digest, canonical source validation and every original ledger payload. It returns fixed source/action IDs, original deadline and admission time with `Created=false`. This grants no replay, new job, claim or provider permission. Missing actions under the surviving admission marker refuse as purged; mismatched payloads refuse as conflict. Deleted jobs are never re-enqueued. A missing private plan cannot be reconstructed by admission.

The existing outbound worker/executor handles these actions. Fresh provider authorization, pacing, one-use claims, uncertain-outcome terminalization, successful echo markers and shutdown gates remain in force. Queue admission does not promise delivery or ordering among effects. The new store operation does not select a worker, open a pool or bypass the retained-send opt-in.

## Read-only original outcome recovery

[Issue #319](https://git.subcult.tv/subculture-collective/overlaid/issues/319) adds `AutomationStore.LookupOperatorChatAdmission(ctx, actor, request, digest)`. This explicit managed-store read resolves only the initiating actor's original request and exact reviewed plan digest. It repeats source/admission role and schema validation, fresh configure permission and tenant/lifecycle read fences, then regenerates the complete original canonical plan. It requires no active sender, controller or current selected version, and still works after deadline expiry, target revocation or allowance reduction while the private source remains retained.

The result contains source/run/digest, original deadline/admission time and 1–16 action summaries in original traversal order. Summaries expose only action ID, sequence, fixed state/code/failure and retry duration. Message text, target, provider message ID, payload/claim hashes, credentials and raw provider diagnostics are excluded. The admission time must fall within the original prepared-plan/deadline interval. One SQL statement snapshots all mutable action outcomes without taking execution row locks; private payload comparisons remain inside that query.

Every original action must match the canonical source, text, payload hash, capability, key, target and deadline. Missing, extra, mismatched or contradictory rows refuse the whole result; no partial prefix is returned. Known pending/running/delivered/rejected/uncertain combinations and fixed failure vocabulary are checked before projection. A pending record can remain pending after expiry: lookup does not terminalize it or infer delivery. Retry metadata describes the retained outcome and grants no scheduling or replay permission.

Prepared-but-unadmitted and missing private input return the existing fixed missing result. Deleted actions under a surviving admission marker return purged. Neither outcome proves a prior request failed or authorizes a replacement UUID. Lookup never admits, repairs, extends a deadline, reserves allowance/pacing, claims, re-enqueues, calls a provider or writes audit/trace data. No HTTP, dashboard or startup consumer is selected in this unit; those callers still need owned admission, scoped unresolved-intent handling and fixed transport projection.

## Migration and lifecycle

Apply `0044_operator_chat_admission.sql` before starting this binary. Stop older application writers and queue consumers before migration. The migration adds nullable `engine_source_id`, exact-one-of-three source validation, original-target/deadline cascading references, text-only engine shape and a source/effect unique index. Existing actions, jobs, claims, deadlines and receipts are preserved. Replacing the old source-check constraint name intentionally makes older runtime startup refuse the new contract. Already-running older processes must be stopped; a startup guard cannot invalidate their pools.

`engine_operator_chat_admissions` is forced-RLS metadata with tenant-runtime SELECT/INSERT only. Its immutable primary key references the original source-plan marker. Queue, pacing and credential roles receive no access. Admission repeats exact column, role, policy and validated nondeferrable constraint checks. Runtime startup requires forced RLS and the exact outbound source/target/deadline contracts.

Deleting the private plan through run/member/connection/retention lifecycle cascades its ledger actions and their jobs. The admission record survives with the original occurrence's plan marker, preventing recreation after private deletion. Tenant/occurrence deletion removes both metadata markers. Metadata-only exports and receipts include the engine source ID; private effect text, source bodies and raw request keys remain excluded. Admission records are bounded by the existing 10,000 source-plan markers and contain no viewer capture.

Rollback must preserve admission and source markers, ledger claims and jobs. Stop the new admission caller/consumers first. Older binaries deliberately fail startup against this schema; use a compatible runtime with engine admission disabled. Reverting the source constraint or deleting engine rows to force an older binary to start is not a safe rollback. This change has not been deployed or qualified against a real provider.

## Account recovery transport

`POST /api/tenants/{id}/automations/lookup-chat-admission` accepts exactly `requestId` and `digest`. The existing account session, Origin/CSRF and fresh configure checks bind the initiating actor and workspace; bootstrap/operator authority is refused. Responses use `Cache-Control: no-store` and explicitly project source/run/digest/deadline/admission time plus action ID/sequence/state/code/failure/retry duration and each action's fixed `notBefore`/`deadline` window. Lookup compares both against the regenerated plan; a changed window is a conflict, never a repair. The dashboard shows the window only for delayed replies. Existing fixed automation errors apply; missing or purged outcomes remain unresolved and never admit work.

The route remains available after controller ownership loss and creates no runtime, sender, queue job or provider request. Private text, targets, provider message IDs and claim hashes are excluded. No browser control or delivery admission route is added. New delivery admission still requires an owned controller/runtime boundary and scoped unresolved-intent recovery.

## Application-owned admission

It reuses the existing retained chat owner instead of selecting another worker or dispatcher. Both retained ingestion and retained sending must already be configured and ready. The exact supplied server must still be the live tenant runtime, with matching retained product scope; bootstrap, stale, deleting, legacy and unavailable runtime/owner selections refuse without fallback. No runtime or pool is constructed by this operation.

A five-second operation context combines caller, application and tenant cancellation. Existing authoritative controller-lock and product/queue/pacing/shared-role checks run before invoking the store. The store still rechecks configure permission, original actor/request/digest, canonical source, target, limits and database-clock deadline. Queue admission is not provider permission: the existing executor independently authorizes, paces and claims each effect. An uncertain commit still requires original-request read-only recovery; never invent another key.

The account delivery route described below invokes this operation; no dashboard control or automatic startup path does. Future transport must supply the authenticated actor, frozen request/digest and exact runtime, bind session cancellation, and preserve unresolved intent on all uncertain failures. Existing receipt lookup stays independent of owner readiness. Disposable PostgreSQL race fixtures exercise context bounds, runtime/app cancellation, stale/legacy/bootstrap/unready refusal, one-time admission/no-op identity, controller loss and retained read recovery. Fixture transport rejects provider calls; no real provider acceptance or deployment is claimed.

## Authenticated delivery admission

[Issue #325](https://git.subcult.tv/subculture-collective/overlaid/issues/325) adds `POST /api/tenants/{id}/automations/admit-chat-plan` with exactly `requestId` and `digest`. The shared account session/Origin/CSRF/configure boundary supplies actor/workspace and refuses bootstrap/operator authority. Unknown fields, including text, actor, target, deadline and retry, refuse before admission. A source plan must already exist; this route never prepares one.

The route reads the already-live runtime map and invokes the owned operation. Missing/stale/unready/legacy ownership returns the fixed unavailable response without runtime creation or fallback. Application, tenant, caller and session cancellation remain bound. All source, payload, target, allowance, original deadline and one-use execution checks remain mandatory. Original plan expiry maps to HTTP410 `automation_chat_plan_expired`.

HTTP202 acknowledges new queue admission; HTTP200 with `created=false` acknowledges the same retained admission without new work. Both explicitly project sourceId, actionIds, deadline, admittedAt, created and state `admitted_queued`. That state acknowledges historical admission, not current delivery or effect ordering. Use the separate lookup route for current outcomes; it may report delivered/rejected/uncertain instead. Responses are JSON and no-store. No private message, provider/claim identity or diagnostic is projected.

A missing lookup, network error, cancellation or malformed response leaves the original request unresolved; it never authorizes another POST or replacement request key automatically. Plan preparation and read-only recovery use the separate `prepare-chat-plan` and `lookup-chat-plan` account routes. Dashboard preparation controls hold a frozen intent and recover it by lookup. The dashboard delivery controls below use this route. No real provider qualification or deployment is established by fixture transport.

## Dashboard delivery controls

[Issue #333](https://git.subcult.tv/subculture-collective/overlaid/issues/333) adds a delivery section under chat-plan preparation in the operator rehearsal panel (`OperatorChatAdmissionDesk.tsx`). The codec is `web/src/lib/operatorChatAdmissions.ts`; the state transitions are in `operatorChatAdmissionFlow.ts`.

1. **Hold.** Available only after the preparation section has verified plan metadata for the same original source. The tab stores the reviewed digest, source, run, effect count and original prepared/deadline times. Nothing is sent.
2. **Queue.** After explicit confirmation, the panel re-reads the plan through `lookup` and `lookup-chat-plan`, using read-only transport and storage. The plan must still match the held digest, source, run, count and times. It then stores the `submitted` phase and sends one `admit-chat-plan` POST with only `requestId` and `digest`. A changed plan or a storage failure sends nothing.
3. **Check.** After a lost response, malformed receipt, error or reload, the only control is `lookup-chat-admission`. Missing or purged outcomes stay unresolved; the panel never queues again or generates a replacement request.
4. **Clear.** Explicit acknowledgment removes the tab handle only. It does not cancel queued or sent messages.

Receipts must carry the original source and deadline, exactly the held number of unique action IDs, and an admission time inside the original prepared/deadline interval. Outcome lookups must match the server's state/code/failure/retry combinations, keep strictly increasing traversal sequences and, when a receipt is in memory, the same action IDs and admission time. A queued receipt is shown as queue acknowledgment, not delivery. Retry hints are informational and grant no new attempt. Live provider qualification and deployment remain open.

## Cancelling unsent replies

Account POST `cancel-chat-admission` accepts exactly `requestId` and the reviewed `digest`, under the same session, Origin/CSRF and configure checks as admission. Like the other metadata writers, it requires the live chat controller. The store regenerates the original plan, requires an existing admission and updates only that plan's replies that are still `pending`: they become `rejected` with code `canceled`, an empty failure and no start time. A reply that is `running` may already be at the provider and is never recalled. Finished replies are left alone. The update takes the same row lock the executor's claim uses, so a canceled reply can never be claimed afterwards, and its queued job ends when the executor finds it no longer pending.

The response is `{sourceId, canceledActionIds, canceledAt, state: "canceled_unclaimed"}`. It lists only the replies canceled by this call, in traversal order. Repeating the call is safe and returns an empty list. It never queues, retries or creates a new request. Use `lookup-chat-admission` to read every outcome; canceled replies appear there with code `canceled`.

Migration 0046 adds `canceled` to the outbound code vocabulary. A CHECK (`platform_outbound_engine_cancel`) restricts it to engine rows that are `rejected`, never started and finished, with no failure or retry hint. Startup requires that constraint. An older runtime's lookup would refuse a canceled outcome as malformed and never treat it as a delivery.

The delivery desk's **Cancel unsent replies** button asks for confirmation, sends one cancel request, then reads the outcomes and checks that every reported cancellation shows code `canceled`. It changes no stored intent.
