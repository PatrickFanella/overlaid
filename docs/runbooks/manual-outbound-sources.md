# Retained manual announcement sources

Tracking: [#127](https://git.subcult.tv/subculture-collective/overlaid/issues/127), parent [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24). This is the storage/admission part of the [non-chat source cutover](../superpowers/plans/2026-10-16-outbound-registry-cutover.md). This foundation is used by the [announcement request/UI contract](manual-announcement-intents.md); [sender/controller startup](retained-chat-sender.md) requires explicit selection.

`platformoutbound.Store.AdmitManual` accepts an explicit `newsroom_current` or `newsroom_raffle` intent. A trusted caller supplies the authenticated actor account, a stable caller UUID request key, the active Twitch connection, the sanitized announcement text and any subject viewer identity. The actor must come from authentication, never a user-selected body field. Viewer references must follow the selected item or raffle winner so deletion can remove derived text. This store does not select Newsroom content or authorize publishing an unapproved card.

Source identity hashes the versioned namespace, tenant, actor and request key. The action identity uses a separate manual namespace and one fixed announcement effect. The raw key is not stored. Kind, connection, text and viewer references contribute to an immutable payload fingerprint: changing them under the same request key conflicts. Each source owns one ordinary `chat.send` action, with no fabricated `normalized_chat_events` row and no threaded reply. Reusing a request key within the retained source lifetime returns the same source, action and original deadline without creating another job.

Admission holds the tenant row lock, rechecks current configure permission (owner, manager or editor), and reads the current plan. The same tenant lock serializes normal membership/owner and plan changes. Permission is checked even for duplicates; a key does not authorize receipt access. New work requires the active matching broadcaster connection, combined chat/moderation action capacity and a bounded manual-source count. Unlimited plans retain the 10,000-row safety bound. The database clock stamps the source after admission locks and sets its original deadline exactly two minutes later. Retries cannot extend that saved deadline.

The source, immutable outbound action and existing payload-free `ChatSendArgs` job commit together. Any conflict, quota, permission, cancellation or enqueue failure rolls back the transaction and returns no acknowledgement. `ManualAdmission` contains source/action IDs, whether admission was new and its deadline. It acknowledges durable admission; it is not a delivered receipt or provider message ID. The existing executor still performs fresh sender/capability authorization, pacing and a one-use pre-send claim. An uncertain delivery must not create another source or request key automatically.

Migration `0026_manual_outbound_sources.sql` adds forced-RLS `platform_manual_sources`, a nullable manual source reference on the outbound ledger, an exact-one-source check and a same-tenant/connection cascading foreign key. Chat event references remain unchanged for existing actions. One manual action per source is enforced by an index. The existing River action foreign key and queue/role policy are unchanged; source and content never enter job arguments. Tenant startup requires the new table's forced RLS and validated source constraints. Queue, pacing and execution roles receive no new table grant.

## Lifecycle and exports

Manual sources reference the initiating tenant membership and Twitch connection. Removing that membership, deleting the connection or deleting the tenant cascades to the source, ledger action and job. Connection revocation retains the receipt but blocks new work and is rechecked by the executor. Changing a member's role blocks future admissions; it does not cancel already admitted work. The existing actor and sender authorization boundaries remain distinct.

Viewer deletion removes sources whose saved subject viewer ID or login matches, cascading private announcement text and jobs. Retention removes sources older than the tenant retention period and their derived rows. Store receipts and tenant exports expose fixed source/action metadata; announcement text, actor/subject identities, request keys, payload/claim hashes and connection credentials are excluded from the manual-source export.

Idempotency is limited to retained sources. A lifecycle purge deliberately removes that record; callers must not treat a missing source after purge as permission to replay a prior or uncertain effect. A future HTTP flow must preserve one key for an unresolved intent, make retries explicit and distinguish queued admission from delivered results. It must not synthesize chat events or fall back to the legacy sender when retained admission fails.

## Verification and migration/rollback

Disposable fixtures exercise concurrent identical requests, conflicting payload/kind/binding, exact original deadlines and payload-free jobs, cross-tenant foreign keys, queue-role exclusion, permission revocation while waiting on the tenant lock, zero allowance, cancellation and enqueue rollback. Export/viewer/retention/tenant lifecycle checks remove private input. An explicit executor fixture sends through a synthetic callback once and rejects replay; no real provider is contacted. An upgrade fixture reapplies the migration over pending, running and delivered chat actions and verifies their saved rows/claims/deadlines and job counts are unchanged. The full PostgreSQL verification/race gate remains required.

Apply the migration with administrator credentials before this runtime; never apply it with the product or queue role. Preserve a private backup and stop old writers for the upgrade. No backfill or job catch-up is needed because existing chat rows already have their source and jobs. Keep both the schema and all ledger state during rollback. An older runtime does not understand manual source rows or nullable chat event IDs and must not read/write this state after manual admission has been used. Stop senders and use a compatible build, or restore a matched private database/application checkpoint under a separate recovery procedure. Never remove claimed/uncertain rows to make rollback appear healthy.

The [HTTP/UI intent and receipt contract](manual-announcement-intents.md) supplies queued acknowledgements and locked source-content binding. The [opt-in sender controller](retained-chat-sender.md) supplies startup validation, ownership, readiness/shutdown and rollback guards; broader lifecycle/load acceptance remains unfinished. Live Twitch/OBS and full thousand-channel delivery qualification remain separate work.
