# Shared bot publication and tenant delegation

[Issue #64](https://git.subcult.tv/subculture-collective/overlaid/issues/64) adds metadata publication and tenant consent on top of the [service bot vault](service-bot-vault.md). No OAuth route, desk control, sender switch or provider request is enabled. Existing broadcaster credentials and the current command registry continue their current execution path.

Apply `0012_shared_bot_delegations.sql` with administrator migration credentials before starting this managed revision. It adds a forced-RLS global metadata catalogue and a tenant-scoped delegation table. Runtime pools receive SELECT-only access to available catalogue rows and scoped delegation access. The catalogue has no credentials, ciphertext, key versions or OAuth scopes. Worker pools receive no catalogue access. The service bot administrator can publish metadata but cannot read tenant delegations.

`BotAdminStore.PublishMetadata` requires the current service credential grant revision and current catalogue revision. Catalogue revision zero means initial publication only. Every publication/unpublication advances the catalogue revision and commits with an administrative receipt carrying that catalogue revision. Service credential reauthorization or revocation makes an existing publication unavailable and advances its catalogue revision in the same transaction. Ordinary refresh can update the published login without changing the publication revision. Initial account creation publishes nothing.

`Store.SharedBotCatalog` returns at most 32 available identity records to a tenant member with connection permission. Publication is the service administrator's explicit choice to make a bot identity selectable; it does not establish a Twitch grant or moderator role. Unavailable metadata is visible only to the service administrator. Tenant revocation does not withdraw global publication.

Only the current tenant owner can grant or revoke delegation. `GrantSharedBot` requires the expected active broadcaster subject, published bot ID, service grant revision, catalogue revision and current tenant delegation revision. Zero tenant revision means initial consent only. It records an allowlisted capability set and increments consent revision on replacement. This unit supports chat send/reply/announcement, message deletion, timeout, ban, unban and warning consent. Unsupported capabilities fail closed. Actual platform scopes, role, entitlements and adapter support remain additional execution requirements.

Granting a shared bot clears a tenant-owned bot binding. Binding a tenant-owned bot revokes an active shared delegation. Broadcaster reauthorization or revocation revokes its active shared delegation, clears capabilities and advances the consent revision. Reconnecting even the same broadcaster requires new explicit consent. Reauthorizing an unbound tenant-owned bot alone does not alter a shared delegation.

`ResolveSharedBot` is a trusted execution helper returning consent metadata only. It uses a consistent read transaction to recheck expected tenant consent revision, bot ID, channel identity, selected capability, active broadcaster, lack of an own-bot binding, current publication and service grant revisions. Unpublication/republication cannot revive old tenant consent because the catalogue epoch changes. A changed service grant also requires publication and fresh tenant consent.

The resolved result is a snapshot, not an authorization token. A catalogue withdrawal can race a consent transaction; retained consent then fails the next resolution. Future outbound execution must recheck provider capabilities/current bot role, resolve credentials through the separate vault using the retained service grant revision, and revalidate tenant consent immediately before an effect. Consent checks across pools and external provider effects are not one database transaction, and revocation cannot recall a credential already returned to trusted code. This unit does not claim exactly-once provider delivery.

`RevokeSharedBot` affects only that tenant and uses its expected consent revision. Tenant deletion cascades delegation rows, leaving service credentials, catalogue records and other tenants' consent intact. Owner exports use an allowlisted metadata projection. Tenant audit entries contain fixed provider/action fields, never service credentials. Service publication receipts use the existing bounded administrative audit store; receipt failure rolls back publication.

For rollback, stop future shared-bot consumers and preserve database/keyring backups together. Leave the additive catalogue/delegation tables in place. Older binaries cannot maintain these delegation invalidations, so do not perform connection changes through an older binary while a shared consumer is active. Existing broadcaster sending remains available through the previous code. Destructive role/table retirement is a separate operator action.

Disposable PostgreSQL fixtures cover published/unpublished visibility, tenant and role isolation, stale references and capabilities, publication epochs, independent revocation, broadcaster/own-bot transitions, concurrent consent, redacted exports, receipt rollback and tenant lifecycle independence. They use synthetic identities and make no provider calls. Live OAuth, provider role checks and sending remain later work.
