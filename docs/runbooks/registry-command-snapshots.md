# Saved registry command snapshots

Tracking: [#121](https://git.subcult.tv/subculture-collective/overlaid/issues/121), a P2.3 prerequisite under [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24), following merged [atomic reply admission](reply-batch-admission.md).

The processor previously copied command behavior without its saved registry identity. Queued Newsroom execution then matched the current command by name and action, so an edited or replaced command could satisfy that check even when its original snapshot was no longer current. The server now supplies saved identity and an opaque snapshot fingerprint to the existing processor.

`bot.CommandSnapshotFingerprint` hashes a versioned tuple containing the tenant namespace, saved ID, normalized registry configuration and UTC creation/update metadata. It includes enabled state, response, action, response mode, role and cooldown. Empty saved IDs yield no fingerprint. Only the saved ID and digest travel as `registryCommandId` and `registryCommandFingerprint`; no extra response/configuration plaintext enters that metadata. Existing reply text and overlay fields keep their established behavior.

Accepted custom commands retain this metadata through aliases and chat/both/overlay modes. Queued Newsroom requests carry the same fields through the general registry. The Newsroom handler compares both fields with a fresh registry read before its existing role/plan/editorial checks and rejects missing or mismatched snapshots with the existing fixed changed-command error. Configuration edits with unchanged name/action, disable/re-enable and delete/recreate no longer authorize that queued snapshot. A fresh request after processor refresh uses the current snapshot.

This is a comparison against the registry snapshot observed at that read. The digest and timestamp metadata are not a monotonic database revision, an atomic admission fence, provider authorization or a source identity. A concurrent edit after the comparison remains a separate execution/admission concern. The [cutover plan](../superpowers/plans/2026-10-16-outbound-registry-cutover.md) still requires a canonical retained source, stable follow-up keys, one-sender/controller guards and lifecycle/readiness checks before activation. The processor remains the single parser; no separate Newsroom command manager is introduced.

No SQL migration, provider credential change or sender startup registration is required. Older queued events without snapshot metadata fail closed under the new Newsroom check; history remains read-only and is not automatically replayed. A rollback may retain event metadata, but an older handler does not enforce the new comparison and should not consume newly queued requests as a substitute for this check.

Pure tests cover every fingerprinted field, tenant namespaces, UTC location equivalence, aliases and response modes. File-backed server tests prove stale/unbound requests cannot mutate the desk and fresh requests still work. PostgreSQL tests reject another tenant's saved request, reject changed configuration, persist a fresh question and preserve tenant isolation. The full gate is `GOTOOLCHAIN=go1.26.0 bash scripts/ci-postgres.sh`, including make verify and both uncached race suites. No fixture sends a live provider message.

Retained registry replies now use [transactional admission binding](registry-admission-binding.md): command rows for new actions are locked and compared through the ledger/job commit. The fingerprint alone remains a snapshot identifier. Newsroom editorial execution and provider delivery are separate boundaries.
