# Retained outbound chat ledger

`internal/platformoutbound` stores immutable follow-up actions for retained Twitch chat events. This is a storage and scheduling foundation: the application does not yet admit these actions or run an outbound worker. Current broadcaster replies continue through the existing send path. No deployment flag or provider request is introduced.

Apply `migrations/0013_platform_outbound.sql` and `0014_outbound_queue.sql` with the existing administrator migration workflow before starting the new managed binary or any ledger producers. Startup checks forced RLS and the outbound job foreign key. The table grants access only to the existing tenant runtime role; River workers and service-bot administrators receive no additional access. The River tenant policy applies only to the runtime role; setting a tenant context does not let the chat worker lease outbound jobs. File mode is unsupported.

`Admit` derives a SHA-256 action ID from the tenant, connection, retained source event and producer-owned action key. Each new action and its `overlaid_chat_send` River job commit in the same transaction; a failed enqueue rolls both back. Jobs contain only tenant ID, action ID and the original deadline, use queue `chat_outbound`, priority 4 and three maximum attempts. That attempt count is for a future worker's infrastructure handling and does not authorize provider replay. No outbound worker is registered or granted lease access. A repeated identity with matching text and reply parent returns the original action without mutation; a different payload returns `ErrConflict`. The source event and connection must belong to the same tenant and active Twitch channel. Composite foreign keys preserve that relationship. The deadline is the source event's occurrence time plus two minutes, independent of admission or restart time.

Admission locks the tenant with plan changes. The retained action count is bounded by `storedEvents` and a hard ceiling of 10,000 per tenant, including terminal actions; each source event admits at most 16 actions. Unlimited plans still obey those ceilings. Lowering a plan does not invalidate duplicate identity lookup or erase receipts. Expired or deleted sources cannot admit new work.

| Operation | Result |
| --- | --- |
| `Start` on a valid pending action | Commit `running` with a hashed random claim fence before returning the private message and deadline. |
| `Start` on an expired or disconnected pending action | Commit a rejected receipt; return no claim. |
| `Start` on running or terminal work | Return no claim. Restart and concurrent calls cannot replay it. |
| `Finish` with the current claim | Commit delivered, rejected or uncertain status and bounded metadata; clear the fence. |
| `Finish` with a forged, foreign, repeated or recovered claim | Return `ErrFence`. |
| `RecoverExpired` | Terminalize up to 100 actions: pending becomes rejected; running becomes uncertain. Never return work to pending. |

`Finish` detaches from a canceled provider context for a bounded five-second persistence attempt. If persistence fails, leave the durable running fence and recover it as uncertain after its deadline. A late provider result cannot overwrite a recovered receipt. Quota rejections retain a retry hint in nanoseconds, but this store never retries or reschedules them.

Claims and retained message text are internal execution data. Receipt inspection accepts limits from 1 to 100 and exposes only action/event/connection IDs, fixed state/code, provider message ID, failure class, retry hint and timestamps. Owner exports use the same metadata allowlist and omit message text, reply parents, producer keys, payload hashes and claim hashes. Source retention, viewer deletion and tenant deletion cascade to these actions. Deduplication lasts while the source and action are retained; deletion is not a replay mechanism.

The [fenced executor](outbound-executor.md) binds its attempt context to the claim deadline, rechecks current capability through a trusted adapter hook and uses the [restricted durable account/channel pacer](chat-pacing.md) and the [single-attempt Twitch transport](twitch-delivery.md). A stored claim does not grant platform permission. Live adapter/vault integration, worker leasing, moderation priority, explicit retry policy and bot identity activation remain later units. A future worker must compare the job deadline with the ledger deadline before claiming work; neither a job nor a claim can renew it.

Run `bash scripts/ci-postgres.sh` for `make verify`, disposable PostgreSQL integration and the parent/River race suites. Fixtures cover concurrent duplicate admission and claims, immutable payload conflicts, restart, failed-start rollback, cancellation during completion, recovery fencing, quota receipts, plan changes, forced RLS and lifecycle deletion. Queue fixtures also prove action/job rollback, immutable job arguments, concurrent duplicate job suppression, legacy pending-row catch-up and worker denial even with a forged tenant context. They do not send provider messages.

Migration 0013 is additive with no backfill. Migration 0014 adds generated queue identity columns, a composite action foreign key, strict argument/queue bounds and one-job-per-action uniqueness. It schedules only unexpired pending rows left by 0013, without changing their ledger state or deadline; running, expired and terminal rows receive no new jobs. Apply it while ledger producers are stopped to close the upgrade admission window.

Keep ledger producers stopped during application rollback and retain the ledger and inert jobs for inspection. An older producer can create unscheduled rows, so reconcile pending action/job pairs before later enabling an executor. Duplicate admission never recreates a missing job, including after River job cleanup; it cannot serve as a replay mechanism. Current application builds do not yet use these producers. Once an executor is enabled, its rollback must also stop execution before changing binaries or ledger state.

Chat and [moderation follow-ups](platform-moderation.md) share the tenant plan lock, the capped `storedEvents` allowance (at most 10,000 retained follow-ups) and the sixteen-per-source allowance after migration `0019_moderation_actions.sql`. Using both action kinds cannot multiply those bounds. Existing duplicate chat admissions remain no-ops and preserve their original job/deadline. Do not run older admission writers alongside the new ledger once moderation actions are admitted.

[Atomic reply batches](reply-batch-admission.md) admit up to sixteen same-source chat follow-ups and their jobs together; single admission uses the same path. New work checks the database clock after admission locks without renewing its source-derived deadline. This is a [registry cutover prerequisite](../superpowers/plans/2026-10-16-outbound-registry-cutover.md), with no startup activation.

Migration `0026_manual_outbound_sources.sql` adds [explicit manual announcement sources](manual-outbound-sources.md) alongside retained chat sources. Every action has exactly one source kind; manual actions retain a separate source ID and leave the chat event ID empty. `AdmitManual` commits one source/action/job with fresh configure permission and the existing combined allowance. Its receipts expose source metadata, and lifecycle deletion cascades private input. No HTTP or sender startup path selects this foundation yet. Older runtimes cannot safely handle manual rows after admission has been used; preserve schema and claims and use a compatible rollback build.
