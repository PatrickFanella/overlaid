# Retained nuke preview and atomic radiation admission

Tracking: [#179](https://git.subcult.tv/subculture-collective/overlaid/issues/179), [#181](https://git.subcult.tv/subculture-collective/overlaid/issues/181), [#183](https://git.subcult.tv/subculture-collective/overlaid/issues/183) and [#185](https://git.subcult.tv/subculture-collective/overlaid/issues/185), under [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24). This is the internal store boundary for retained nuke batches and zero-target radiation occurrences. The retained HTTP routes below require an explicitly installed moderation owner; default startup still installs none. Legacy nuke execution still refuses that owner before creating radiation. The [single-action HTTP path](operator-moderation-requests.md) is unchanged.

## Preview snapshot

`platformmoderation.Store.PreviewNuke` requires current moderate membership and the exact active Twitch connection. A repeatable-read, read-only transaction observes database time and scans canonical retained chat. Options normalize the message pattern, regex/case mode, delete/timeout operation, lookback (default 30 minutes, maximum 360), history scan (default 100, maximum 250), timeout (default 60 seconds, maximum 14 days) and radiation window (zero through 120 minutes). Invalid ranges fail closed. Radiation input must also satisfy the existing bot-rule pattern/reason constraints.

Targets are ordered by occurrence time and canonical event ID, newest first, and capped at 50 actions. Timeout previews select one target per user; deletes select one per message. Nonmatching, old, future and foreign-channel input is excluded. Retained row metadata must agree with its canonical envelope; PostgreSQL timestamps are compared at their stored microsecond precision. Preview creates no source, action, job, rule, permit or allowance reservation.

`NukePlan` is an immutable in-process value. Its getters return option and target copies. The private binding covers tenant, actor, connection, normalized options, observed preview time, exact retained event IDs and complete envelope fingerprints. The fingerprint is a comparison value, not permission or proof of delivery. The sealed-plan contract below preserves this input across process restarts and browser request persistence. The Chat page uses this snapshot in the saved-request controls described below.

An empty preview with a positive radiation window can admit a `radiation` source and its normalized rule in one transaction. It creates no action, job, provider request or permit. A preview with neither targets nor radiation remains invalid for admission. Ordinary `single` and `batch` source kinds retain their 1–50 action bounds; callers cannot construct the private radiation binding through `AdmitManual`. The existing direct workflow is unchanged.

## Sealed preview persistence

`SealNukePlan` and `OpenNukePlan` use the existing versioned AES-256-GCM vault keyring with a distinct `retained-nuke-preview-v1` purpose. The trusted `NukePlanScope` binds the account, tenant, exact Twitch connection and current opaque `ChatSenderSelection.Binding`. The HTTP routes derive this scope from authenticated request and fresh connection metadata, never browser fields. The binding includes connection/sender generations; opening a token does not establish current role, consent or effect permission.

The encrypted payload preserves normalized options, the original database preview time, exact ordered display targets, private actions/envelope fingerprints and the original payload fingerprint. Opening checks the versioned schema, target/action consistency and fingerprint. Unknown fields, trailing JSON, unsupported versions, changed scope/ciphertext and unavailable keys fail with the fixed `nuke preview unavailable` error. Encoded tokens are bounded at 512 KiB and plaintext at 256 KiB, with at most 50 targets/actions. Oversized previews fail closed.

Retained key versions can open old tokens after active-key rotation. Removing an old key makes its saved previews unavailable; preserve unresolved requests and do not generate replacement request UUIDs. No process-local fallback key is created. The token belongs in an account/workspace-scoped saved request and request body, not an overlay/share URL or audit log. It is neither a public capability nor an authorization token.

Opening a plan performs no database/provider access, creates no rows and does not refresh its timestamp or expand its targets. Old previews remain openable for read-only `LookupNuke`; new `AdmitNuke` still checks the original preview lifetime using database time and fresh permission/connection/target state. The HTTP routes select this codec only under explicit ownership. The Chat page persists the exact sealed preview and supports lookup-only status; configured startup remains unfinished.

## Retained HTTP contract

The account/session and CSRF boundaries protect both routes. They require current moderate permission and an explicitly installed retained owner; absent ownership never falls back to direct moderation. `GET /api/bot/moderation/action` supplies the existing server-projected `mode`, `tenantId`, `actorId` and `connectionId` comparison fields. Both POST routes compare those fields with fresh server metadata and read the opaque connection/sender binding internally. They return `Cache-Control: no-store`.

`POST /api/bot/moderation/nuke/preview` accepts those comparison fields plus an `options` object with `pattern`, `regex`, `caseSensitive`, `lookbackMinutes`, `historyLimit`, `action`, `durationSeconds` and `radiationMinutes`. Requests are bounded at 8 KiB and reject unknown fields or trailing JSON. The response contains normalized `options`, display `targets`, original `observedAt`, `expiresAt`, `fingerprint` and sealed `plan`. Targets use the existing nuke display fields: `eventId`, `messageId`, `userId`, `user`, `message` and `createdAt`. An empty preview without radiation returns an empty plan/fingerprint; it cannot be submitted for admission. Preview is read-only and can remain available with a prepared/stopped owner.

`POST /api/bot/moderation/nuke/request` accepts the same comparison fields, a stable UUID `requestKey`, the sealed `plan` and a boolean `retry`. It accepts at most the 512 KiB token bound plus 4 KiB of envelope overhead and rejects unknown fields/trailing JSON. New requests first look up the exact original occurrence. Only a missing occurrence with `retry: false` proceeds through the ready owner/controller/exact live-runtime guard and `AdmitNuke`. The caller must save the exact intent before its first POST; it must never automatically generate a fresh UUID or switch to direct execution after an error.

`retry: true` is lookup-only, including after consumer stop. Missing/purged outcomes, changed account/workspace/channel/mode or connection generations, and unavailable preview keys stay unresolved; lookup never recreates work. The response contains `mode: "retained"`, `queued`, `radiationOnly` and the fixed metadata `receipt`. HTTP 202 means at least one action is pending/running. HTTP 200 reports terminal action metadata or a configuration-only radiation occurrence; it does not imply that every action delivered or that a radiation rule is currently enabled. Read the individual receipt states. Status never echoes the sealed plan, request UUID, pattern, display targets or private action input.

The legacy `/nuke/dry-run`, `/nuke/execute` and radiation rollback endpoints retain their existing behavior. The direct execute path still refuses installed ownership before effects. The routes add no environment switch or default moderation worker startup. The existing Chat panel selects the appropriate API from the server-projected mode.

[Issue #186](https://git.subcult.tv/subculture-collective/overlaid/issues/186) repairs the radiation start boundary. Under retained ownership, both the canonical occurrence and receipt times must be present and at or after the rule's saved creation time. They come from the private source context bound to the actual retained event/projection; mutable display timestamps and processing time cannot make old input eligible. Missing/unbound source context fails closed. Direct/file mode compares its original internal event timestamp with rule creation. Ordinary manual rules keep their existing behavior, and the expiry/exemption checks still apply.

A delayed pre-creation chat job therefore cannot receive an independent radiation action just because it is processed after the explicit nuke/radiation transaction. The selected batch remains frozen; later matching source input can still receive one source/rule action. This timing check grants no provider authorization or claim and never replays a claimed action.

## Chat page saved requests

The existing nuke planner in `/dashboard/chat` obtains the server mode and saves its exact private preview, normalized input, connection comparison and sealed plan in account/workspace/API-scoped `sessionStorage`. Reload restores the original targets and expiry without renewing the preview. Review confirmation resets on reload. Editing an unsubmitted draft invalidates its saved preview. The history scan limit is separate from the retained 50-effect cap, and the panel displays every selected target. Zero-target previews with positive radiation can be reviewed and submitted; empty effect-free previews cannot.

Before the first execution POST, the browser saves and reads back one UUID with that preview. Every later retained status check uses the same plan/key and `retry: true`, even if the first POST never arrived. It never replans, changes mode, creates a replacement UUID or calls direct execution after retained refusal. Response loss, missing/purged receipts, unavailable keys, scope changes and malformed/contradictory responses remain saved. Inputs and planning stay disabled until explicit acknowledgment. Account/workspace changes fence asynchronous results and keep each scope's saved request separate.

The panel reports pending/running/delivered/rejected/uncertain counts rather than treating HTTP 200 as batch delivery. A radiation-only receipt acknowledges configuration with no message jobs. An original radiation rule ID does not prove current existence or enabled state; the panel refreshes the normal rules list and keeps explicit radiation rollback separate. Clearing a saved request neither cancels work nor disables a rule. All outcomes, including terminal receipts, stay saved until the operator checks Twitch and explicitly clears the request; a fresh preview/review is then required for another execution.

Direct mode keeps its existing rescan and bounded execution API. It saves the request before POST too, but it has no retained lookup contract: an existing direct request cannot be sent again automatically. The operator must check Twitch and acknowledge it first. Session storage survives reload in the same tab; closing that tab ends its local persistence. Storage refusal blocks submission. The sealed preview, private display input and request key never belong in share/overlay URLs or logs.

## Atomic admission and retry

`AdmitNuke` requires the same tenant/actor and a stable request UUID. It reuses the [operator occurrence](manual-moderation-sources.md) tenant lock, fresh moderate permission, active connection, shared action/source limits and atomic source/action/job transaction. It reconstructs only the selected targets and rejects changed, deleted, mismatched or no-longer-matching input. It does not expand the batch to later arrivals. New admission checks the preview's two-minute lifetime with database time after the admission locks and target reads. The new operator occurrence then gets its own fixed two-minute effect deadline; an old viewer message does not set or renew that deadline.

If requested, the normalized enforced radiation rule commits with the source, every action and every job. Its ID is derived from tenant/source identity; creation/update timestamps and expiry use the same database occurrence clock after admission locks, and its timeout matches the preview's selected duration. A later job or rule failure rolls back the whole transaction. No provider request occurs during admission.

An identical request returns its original IDs and deadline, including terminal outcomes. It never recreates removed actions or a deleted/disabled radiation rule. Changing options, target input or preview identity under the same UUID conflicts. `LookupNuke` reads only the original fixed metadata and never reconstructs missing work. A returned radiation rule ID identifies the original configuration; it does not say that the rule still exists or is enabled. Action IDs retain the manual store's exact-key ordering, independently of preview display order. Radiation-only status returns empty `actionIds` and `receipts` arrays; it acknowledges the configuration transaction, not provider delivery. These occurrences count against the same source capacity and retain membership/connection/tenant and retention cascades. Duplicate requests do not charge source capacity again.

Radiation is ordinary tenant bot configuration with its own explicit disable/delete and expiry behavior. Target-viewer deletion removes private batch actions/jobs, including nuke timeouts, while leaving that general rule unchanged. Disabling radiation prevents future rule matches; it does not rewrite already queued effects. Source membership/connection/tenant and retention cascades remain in force. Source/action exports and status contain fixed metadata only; normal authorized bot-configuration exports retain the rule as before.

## Migration and compatibility

Migration `0029_nuke_timeout_targets.sql` adds a separate nullable cascading target reference for manual nuke timeouts. It preserves the existing delete/user-action constraint, source identities, payloads, job IDs, deadlines, claims, role grants and forced-RLS policies. The new column is excluded from metadata exports. Current runtime startup requires the exact validated kind and cascading foreign-key constraints; old or weakened schemas fail startup.

Migration `0030_radiation_only_sources.sql` replaces the source kind/count checks with an exact union: `single` has one action, `batch` has 1–50, and `radiation` has zero. It changes no populated source/action/job/claim values or role grants. Startup requires the exact validated union; old or broadened source contracts fail closed. Earlier binaries cannot interpret radiation-only sources, so stop older writers before using this contract.

Apply the migrations with administrator credentials before using this binary, following [tenancy migration and recovery](tenancy-and-recovery.md). Preserve populated ledgers, jobs, claims, nuke-target references and radiation configuration on rollback. Do not drop the target column or delete pending work as a rollback shortcut; stop writers and review binary/schema compatibility or use the reviewed backup procedure. No migration/backfill is added by the radiation timing repair: existing rows, IDs, claims and jobs are retained. Previously written rule timestamps are not rewritten; review or disable old radiation configuration before live qualification. Stop retained writers before rolling back to a binary without the start guard, which can reintroduce backlog matching. These units perform no production migration or activation.
