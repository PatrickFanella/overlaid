# Service-owned bot vault

[Issue #62](https://git.subcult.tv/subculture-collective/overlaid/issues/62) adds the administrative storage boundary for a pool of shared Twitch bot identities. `BotAdminStore` uses a separate restricted database pool. Application startup does not open it. The [operator CLI](service-bot-admin.md) supplies service OAuth and publication without exposing tenant HTTP or changing the sender. The [delegation store](shared-bot-delegation.md) adds explicit publication and tenant consent. Tenant-owned bots remain in the [tenant store](bot-accounts.md).

Apply `0011_service_bot_accounts.sql` using administrator migration credentials. It creates the `overlaid_bot_admin` NOLOGIN group and forced-RLS service account/audit tables. Migration 0012 adds its metadata catalogue access; apply both before opening the updated administrative store. Product and River worker roles receive no grants or policies on these tables. No login credential or production DSN is created. A future service component needs a separately provisioned login with only this group's privileges, access to the deployment vault keyring, and the same application database/schema. Keep its DSN out of browser responses and tenant configuration.

`OpenBotAdminStore` validates a non-owner, non-superuser, non-bypass role. It requires both service tables to have forced RLS and their single administrative policy, the expected table grants, and no access to other application tables in the configured schema beyond the metadata catalogue. Reachable role memberships are inspected as well as effective permissions, including NOINHERIT memberships that could be activated with SET ROLE. A product, worker or migration-owner DSN fails closed. Keep this role separate from account control-plane roles. The check covers the configured schema; operators must also avoid granting access to unrelated schemas/databases. Use dedicated credentials and do not change role grants while a store is active. PostgreSQL privileges and RLS still apply after startup, but startup validation is a snapshot.

`SaveValidated` accepts the internal version 1 credential envelope after the trusted OAuth adapter validates the Twitch client and subject. Zero expected revision means creation only. Reauthorization requires the current revision and increments it. Revocation also requires and increments the current revision, clears ciphertext/key version/scopes, and retains identity metadata. The pool is capped at 32 retained accounts, including revoked identities; admission is serialized across processes. This is a storage safety bound. Account deletion/retirement remains a later contract; tenant consent uses the separate delegation store.

Ciphertext uses the existing versioned AES-GCM keyring with a service namespace, provider, account ID and key version as authenticated data. It cannot be substituted for a tenant credential or another service account. Account lists expose identity, scopes, revision and revocation only; the internal `BotCredential` returned by resolution must never be serialized into a browser response, generic config or audit document.

`Resolve` requires an active account and expected grant revision and locks the account row across refresh. Callbacks must validate the provider client/subject, use the supplied context and bounded network timeouts. Subject changes, expired credentials and callback failures roll back; provider error details are replaced with fixed errors. Successful refresh updates current login/scopes/tokens and rotates encryption to the active key. Ordinary refresh retains the grant revision. Future effect execution must inspect current grants/scopes and bot role at execution; a revision or retained identity alone does not grant permission to send or moderate. Revocation cannot recall a token already returned to trusted code.

Grant, refresh and revoke commit with a fixed-field administrative receipt: account ID, grant revision, action, database session principal and timestamp. No tokens, ciphertext, provider errors or caller-supplied audit text are retained. Receipt maintenance serializes after the account lock and prunes to 1,024 newest rows and 90 days on each successful mutation. Reads return at most 100 receipts. With no mutations, old receipts remain until the next mutation; no scheduler is enabled by this unit. Receipt failure rolls back the account change.

Service accounts have no tenant foreign key. Tenant export/deletion cannot expose or delete them. Tenant assignment uses scoped consent, independent revocation and execution revalidation through the delegation store, without giving tenant pools direct access to this vault. No service identity is automatically copied into `platform_connections` or `bot_accounts`.

For rollback, stop future service components using this boundary and preserve database/keyring backups together. Leave the additive tables and NOLOGIN group in place. Earlier application revisions continue using their broadcaster credentials. Destructive account/table/key retirement requires a separate operator action; keep old keys until rotation of every retained credential is verified.

Qualification uses synthetic credentials and a disposable PostgreSQL database. Tests cover restricted and reachable role privileges, independent tenant lifecycle, grant revisions, serialized refresh, restart/key rotation, ciphertext binding, failure rollback, revocation, admission and receipt limits. They make no real provider requests and do not qualify live OAuth or Twitch delivery.
