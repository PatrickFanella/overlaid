# Transactional registry reply admission

Tracking: [#125](https://git.subcult.tv/subculture-collective/overlaid/issues/125), parent [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24). This extends the explicit [source-bound collector](registry-reply-collection.md) after PR #124. [Explicit retained sender startup](retained-chat-sender.md) selects it; this admission layer adds no SQL migration or role grant.

`platformoutbound.AdmitRegistryBatch` accepts bounded `RegistryReply` values. Every request must carry a saved command ID, its tenant-scoped snapshot fingerprint and one supported effect kind. The request key must equal the existing version-one registry/effect key. Custom chat responses and Newsroom current each have one effect at position zero. Their current contract sends an ordinary channel message, so threaded `ReplyToID` requests are rejected. Rendered text and random display IDs remain outside the key; immutable payload comparisons still reject changed text for an existing identity.

Admission first locks the tenant row, then reads the assigned plan in a new statement. Combining that read with a joined row lock can return no row when PostgreSQL rechecks a concurrent plan reassignment against the old join; the separate read avoids that race. The tenant lock holds the assignment through commit. Plan definitions remain administrator-owned and are read as configured; this change does not lock global plan definitions or grant runtime plan-write privileges.

After checking existing action identities, admission locks the command rows used by new actions in sorted ID order with `FOR SHARE`. Each row must exist in the same tenant, remain enabled and match every field/timestamp in the saved snapshot. Each new effect must fit that saved action and response mode: `newsroom-current-v1` requires `newsroom_current`; `chat-response-v1` requires a non-Newsroom command in `chat` or `both` mode. Command entitlement uses the assigned plan's `commands` limit and the existing `created_at,id` rank. Inserts already serialize on the tenant limit lock; normal registry updates cannot change creation identity or rank. The selected command rows stay locked through the ledger/job commit, blocking edits, disabling and deletion until that admission finishes.

The same transaction then performs the existing active-connection/source/deadline, combined chat/moderation allowance, ledger and payload-free job checks. Any stale snapshot, unsupported binding, plan failure, cancellation or enqueue failure rolls back all new actions and jobs. No partial batch results are returned. Command-row lock waits cannot extend the original source deadline; admission still checks database time after acquiring source/connection locks.

Identical existing actions remain metadata-only noops, including after the command changes or is deleted, the plan changes or the connection is revoked. A mixed batch checks snapshots and entitlements only for new actions. It does not reauthorize or replay prior effects. Existing keys, action IDs, payload hashes and jobs remain compatible with PR #124. The generic `Admit`/`AdmitBatch` foundation remains available for other explicit producers; registry collection now uses the guarded method exclusively.

This defines an admission cut point. Later registry edits do not cancel already admitted immutable actions. It is not a monotonic revision scheme or a transaction spanning Newsroom editorial changes, display/history publication or provider delivery. Fresh selected-sender authorization and one-use ledger claims remain mandatory at execution.

## Verification and activation boundary

Disposable PostgreSQL fixtures place edits, disabling and deletion ahead of the snapshot lock and confirm rejection with no new actions/jobs. A ledger-table lock then holds admission after snapshot validation; a second editor is observed waiting specifically on that admission backend until commit. Other cases cover concurrent plan reassignment, command limits, foreign snapshots, unsupported effect/key bindings, mixed old/new batches, cancellation while waiting, and noops after a saved configuration changes or disappears. Existing collector fixtures continue to cover custom/Newsroom behavior, source lifecycle, publication failures and zero provider transport requests. The full PostgreSQL verification/race gate is required.

The [manual request/UI contract](manual-announcement-intents.md) supplies non-chat identities and truthful acknowledgements, while [retained sender startup](retained-chat-sender.md) supplies controller/pool/readiness/shutdown and rollback guards. Broader lifecycle/load and live acceptance remain unfinished. No live Twitch/OBS or thousand-channel delivery qualification is claimed.
