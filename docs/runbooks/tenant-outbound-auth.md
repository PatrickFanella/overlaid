# Tenant Twitch outbound authorization

`twitchoutbound.New` constructs a trusted authorization adapter for `platformoutbound.NewExecutor`. It uses the existing tenant credential vault, immutable product scopes and `twitchsend.SendUserMessage`. It opens no new pool and registers no worker at application startup. The current broadcaster sender and Chat command manager keep their existing path. This adapter is available for explicit fixture/client construction until the outbound cutover is reviewed.

Apply `0017_sender_selection.sql` after the prior platform migrations through the administrator workflow. The migration adds a connection sender revision and a trigger: changing a bot binding, broadcaster identity, connection grant time or revocation advances the revision. A refresh-only ciphertext update preserves it. Direct revision writes cannot erase or forge that history through an ordinary update. This distinguishes A-to-B-to-A selection changes and same-subject reauthorization from an unchanged sender. Keep the additive column and trigger during rollback.

The adapter supports `chat.send` and `chat.reply` through user tokens:

- With no active own/shared selection, use the connected broadcaster's exact subject.
- With an explicit tenant-owned bot binding, resolve only that active account for the expected broadcaster. A separate bot must currently be a moderator in that channel under this adapter's conservative product policy. Check it through a fresh filtered Get Moderators request, not retained badges or onboarding status.
- An active shared-bot selection fails closed, including a stale/unpublished catalog grant. It never falls back to the broadcaster. Shared service-vault resolution and execution remain a separate unit; the tenant/queue pools still have no service-vault permission.

The sender's validated token must include `user:write:chat`. For a separate own bot, the broadcaster must additionally authorize `moderation:read` or `channel:manage:moderators` for the role lookup. Existing default broadcaster scopes are unchanged. Before opting into this future adapter, explicitly add the required lookup scope to `TWITCH_SCOPES` and reconnect the broadcaster through owner-controlled OAuth. Merely changing environment configuration does not grant a scope. Twitch's [Send Chat Message](https://dev.twitch.tv/docs/api/reference/#send-chat-message) accepts a user token for its own sender subject, while [Get Moderators](https://dev.twitch.tv/docs/api/reference/#get-moderators) requires the broadcaster subject and the lookup scope. The moderator requirement here is product policy for separate bot identities; it is not a claim that all user-token chat requires that role.

Every authorization validates the current token at Twitch's [validation endpoint](https://dev.twitch.tv/docs/authentication/validate-tokens/) and checks the configured client ID, exact expected subject, expiry and returned scopes. A token within thirty seconds of expiry, or a validation rejection with a retained refresh token, may refresh once through [the documented token endpoint](https://dev.twitch.tv/docs/authentication/refresh-tokens/). Validate the refreshed token before persisting or using it. Refresh uses the existing tenant-first connection/account locks and encrypted writeback. A failed validation/refresh does not reuse an old token. Credentials stay inside trusted adapter closures and never enter action/job arguments or errors.

Authorization has a ten-second bound capped by the action deadline, five-second HTTP request timeouts, fixed provider endpoints, redirect refusal and a 32 KiB response bound. Unavailable/malformed provider responses produce fixed preparation errors; known missing grants or mismatched identities deny authorization. Context cancellation prevents an unbounded lookup. Existing provider-side token rotation is outside the database transaction; recovery of a failed refresh/persistence still requires the retained vault procedure.

The adapter returns an opaque selection fingerprint. The executor compares both sender subject and this binding fingerprint before and after its committed claim. After refresh and role checks, the adapter also verifies that the local selection stayed unchanged. Before the send callback invokes transport, it checks the action/channel/reply mode, reserves the effect call, and rereads the current binding and plan. A changed selection, revoked connection or disabled/exhausted allowance rejects the callback. No database lock spans the provider send; local/provider revocation and an external effect cannot be one transaction. Twitch still enforces the token and channel rules at the endpoint.

Current plan limits must permit retained events and outbound HTTP calls. Each moderator lookup and send attempt reserves one call through the existing tenant usage store, including a final reservation immediately before send. OAuth validation/refresh remains credential-control traffic, as in onboarding, and does not consume the product HTTP allowance. Reservations are not refunded after later rejection. No new plan feature or billing semantics are introduced.

Run `bash scripts/ci-postgres.sh`. The adapter fixtures use disposable PostgreSQL plus an in-memory HTTP transport. They cover broadcaster/own-bot delivery, fresh token/role validation on both sides of the claim, serialized refresh, unexpected token expiry, changed/revoked subject/scope/role/plan, selection cycles, same-subject reauthorization, stale callback rejection, quota exhaustion, cross-tenant denial, canceled lookups, bounded malformed/oversized/redirect responses, shared selection denial and durable no-replay. Existing executor, worker and tenant-vault regressions run alongside them. No Twitch messages or production credentials are used.

This unit does not activate bot sending, qualify live OAuth grants, or provide shared-bot execution, moderation-action scheduling, priority or conduit transport. Continue with the restricted shared service-vault adapter, then the remaining priority and opt-in cutover gates.
