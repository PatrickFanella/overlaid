# Parsed variable template cache

Phase 3 V2a, tracked by [#272](https://git.subcult.tv/subculture-collective/overlaid/issues/272), adds an explicit in-memory cache in `backend/internal/variables/cache.go`. No application caller constructs it. Syntax-1 rendering, conversion preview, saved versions and dispatcher selection remain separate work.

`NewCache(total, perTenant)` requires total entries in 1..256 and per-tenant entries in 1..32, no greater than total. There is no unlimited mode. Each entry is keyed by the exact canonical nonzero lowercase tenant UUID, syntax version and SHA-256 of original source. A hit also compares original source, so a hash collision cannot return another template. Canonical identity does not authenticate a tenant; a future caller must derive it from its authorized scope.

`Parse(tenant, source, version)` returns an immutable `Template`, a cache-hit flag and an error. Only successfully parsed syntax-2 templates enter the cache. Unsupported versions, oversized sources and malformed input retain nothing and do not change recency. Hits move to the front of one LRU list. Insertion evicts the tenant's oldest entry when its limit is reached, then the global oldest entry if needed. No per-tenant history or negative-result cache survives eviction.

Source and AST retention are bounded by entry count multiplied by the existing parser limits: 4 KiB original source, at most 4 KiB decoded literal text, 256 nodes and 16 nested calls per entry. Node structs, bounded slice capacity, list/map overhead and the fixed tenant/hash key add memory beyond those text sizes. These are structural bounds, not an exact Go heap-byte measurement or a process memory limit. Caller-held templates and simultaneous callers' input are outside the cache's retained-entry bound.

Parsing, LRU changes and `PurgeTenant` share a mutex. The critical section performs bounded pure parsing and scans at most 256 entries; it runs no callbacks, provider requests or rendering. Purge cannot be followed by a delayed insertion from an earlier cache operation. A new explicit parse after purge may repopulate. Purge releases the cache's references; previously returned immutable templates remain valid and may retain source until their caller releases them. A future application integration must call purge on tenant lifecycle invalidation and handle any templates it holds separately. There are no background timers, goroutines, tombstones or persistent rows.

Entries retain private source text. Do not expose cache contents through logs, public statistics or exports. Captured snapshots, rendered outputs, clocks, seeds, provider values and authorization decisions are never stored here. Do not copy a cache after use. Nil and zero-value caches fail with fixed `variable_cache_config`; invalid tenant identities fail with `variable_cache_tenant`. Parser failures preserve their fixed code and source span.

Verification covers tenant isolation, source identity, collision defense, both eviction limits, invalid bounds/identities/parse input, accessor mutation, concurrent parse/purge and empty post-purge state. Run focused package races and `make verify`; this mutable concurrency unit also runs the repository's disposable PostgreSQL gate. These checks do not establish application integration, live provider acceptance or Phase 3 completion.
