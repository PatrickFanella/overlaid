# Restricted shared-bot execution

`tenancy.OpenBotExecutionStore` opens a separate credential-execution pool. `twitchoutbound.NewShared` explicitly supplies that pool to the existing trusted authorization adapter after checking database, schema, server address and port against its product store. [Explicit retained sender startup](retained-chat-sender.md) supplies this optional pool with `OVERLAID_BOT_EXECUTION_DATABASE_URL`. Without that custody, shared selection fails closed. Default sending and the general Chat command manager keep their current paths.

Apply `0018_shared_bot_execution.sql` through the administrator migration workflow before using the updated service administrator CLI or execution store. It adds the non-login `overlaid_bot_executor` group, refresh-column privileges, published/active vault visibility, catalogue read access and a bounded receipt table. Provision a separate non-owner login inheriting only that group when a later reviewed deployment needs it. This migration creates no production password and grants no tenant, chat-worker, outbound-worker or pacing role vault access.

The execution role can read active service accounts only while their catalogue entry is available. It can update ciphertext, key version, credential login and scopes. It cannot insert/delete accounts, change provider subject or grant revision, revoke grants, publish/unpublish identities, edit tenant consent or read the operator audit. The separate administrator store retains those controls. Startup validation checks reachable memberships, including memberships without inheritance, private table/column grants, owner/bypass/role-administration privileges, schema creation rights, exact applicable forced-RLS policies and the receipt trigger. Combining administrator/execution roles is rejected by both constructors. The opt-in controller repeats metadata validation during its heartbeat and effect fences. Standalone constructor validation is not a continuous monitor of later operator grants.

`BotExecutionStore.Resolve` requires an exact account ID, grant revision and catalogue revision. It locks the service account, checks active publication, decrypts the account-bound credential, invokes a bounded trusted validation/refresh callback, checks the same subject/expiry and publication again, then commits encrypted writeback with a fixed-field refresh receipt. Normal publication, reauthorization and revocation serialize on that account lock. Scope/client validation still belongs to the provider callback; retaining a credential alone grants no effect permission.

The execution receipt is separate from the operator grant/publication audit and from delivery receipts. One row per service account records only `bot_account_id`, `revision`, `catalog_revision`, `refreshes`, `principal` and `refreshed_at`. The existing bounded service-account pool bounds row count. The refresh count measures committed credential-resolution/writeback cycles, not OAuth refresh HTTP requests. The database stamps the session principal, timestamp and monotonic refresh count; column grants prevent callers supplying those fields. The trigger checks current grant/publication metadata and pins trusted schema lookup before `pg_temp`. A failed receipt write rolls back credential writeback. These rows do not enter tenant exports and contain no token, message, provider error or tenant chat payload. Administrator access to this table is read-only; the existing administrator grant/publication history retains its prior contract.

A shared authorization attempt follows these gates:

1. Resolve the active tenant/channel selection and its fingerprint, including delegation and current catalogue identity. Unsupported shared execution still fails closed with the ordinary `twitchoutbound.New` constructor.
2. Revalidate tenant consent for the requested chat capability and exact delegation, grant and catalogue revisions through the immutable product scope. Validate active publication independently through the execution pool.
3. Validate/refresh the broadcaster and selected shared user's exact OAuth client, subject, expiry and returned scopes using the existing bounded HTTP adapter. The shared identity must retain `user:write:chat` and `user:bot` under this product policy. A separate shared user must pass the same fresh moderator lookup as an own bot; the broadcaster needs `moderation:read` or `channel:manage:moderators`.
4. After a committed outbound claim, repeat authorization and compare both sender subject and binding fingerprint. A changed/revoked consent, unpublish/republish, service reauthorization, changed own/shared selection, role, scope or plan cannot reuse the earlier approval.
5. Immediately before transport, reserve the effect call and reread selection, plan, tenant consent and current publication. Send once with the selected shared user token through `twitchsend`; retain the existing echo, ledger and pacing completion fences. No quota hint or uncertain outcome authorizes replay.

This unit uses a user access token for the selected shared identity. It does not introduce app-token sending, conduit transport or a Chat Bot badge guarantee. It does not grant a channel capability merely because service OAuth or publication succeeded. Local/provider revocation and an external send are not one transaction; final local checks and Twitch's endpoint authorization bound that gap. The adapter still obtains fresh provider role checks on both sides of the claim. See [tenant authorization](tenant-outbound-auth.md) for request bounds and HTTP allowance accounting.

Run `bash scripts/ci-postgres.sh`. Fixtures use disposable PostgreSQL and in-memory HTTP transports. They cover published-only SQL visibility; refresh-column and private-table denial; unsafe/reachable roles and broad policies; serialized refresh/restart/key rotation; receipt rollback, stamping and temporary-table shadowing; refresh/revocation ordering; cross-database rejection; actual shared sender identity; independent consent/publication/grant revocation; publication epochs and reauthorization; capability/role/scope/plan/selection changes; stale send callbacks and no replay. Existing tenant-owned, administrative, pacing and queue fixtures run alongside these checks. No live provider messages or production credentials are used.

Rollback before activation stops any explicitly constructed client and retains the additive role, policies, receipt state and encrypted credentials. Do not delete outbound claims or replay uncertain sends. Earlier administrator binaries expect the older policy count; use the updated CLI after migration or a separately reviewed compatibility rollback. The next roadmap unit is priority-aware scheduling and pacing visibility, followed by opt-in outbound integration. No application environment flag or production pool activation is added here.
