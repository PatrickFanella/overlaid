# Restricted outbound worker

`platformoutbound.NewClient` connects the fenced executor to River through a separate restricted service pool. It leases only `overlaid_chat_send` jobs in `chat_outbound`. Only [explicit retained chat startup](retained-chat-sender.md) constructs its separate pool and controlled client. Default broadcaster replies keep their direct path; the [tenant Twitch authorization adapter](tenant-outbound-auth.md) supports broadcaster/own-bot construction. The explicit [shared adapter](shared-bot-execution.md) adds restricted service credential resolution. Moderation has its [separate priority lane](moderation-priority.md); its separate [configured consumer](moderation-consumer.md#configured-opt-in) supplies startup, while broader controlled qualification remains open.

Apply `0016_outbound_worker.sql` through the administrator migration workflow after the ledger, outbound queue and pacing migrations. It creates the non-login `overlaid_outbound_worker` group, grants the required River metadata/sequence access, and adds a send-kind policy to the already forced-RLS `river_job`. It neither creates a production login nor grants access to product, credential or pacing tables. Retain the existing migration and private backup/restore procedure.

A future deployment must provision an isolated non-owner login inheriting only `overlaid_outbound_worker`. Keep it separate from `overlaid_worker`, `overlaid_runtime`, `overlaid_pacer` and the bot administration role. The executor still needs its independently validated product and pacing pools and a trusted authorization adapter. The caller owns all pool lifetimes. The sender runbook defines the explicit configuration and persistent mode guard.

Both outbound and chat clients use `platformqueue.Validate` before construction. It rejects table owners, superusers, RLS bypass and role-administration privileges reachable from the current or session user, including memberships without inheritance. Reachable roles must have no private-table access in the product schema, no dangerous River table privileges, and no write access to River migration history. The client requires River metadata DML and exactly one applicable job policy with the expected name, role scope, command and kind predicates under forced RLS. PUBLIC policies and combined chat/outbound memberships fail closed. Database, schema, server address and port must match the immutable product pool. The opt-in application controller repeats role/policy checks during its heartbeat, admission, authorization and transport fences; standalone clients retain construction-time validation.

The worker uses the [tenant-fair driver](tenant-fair-leasing.md), requiring migration 0023 before explicit construction. It selects ready jobs in retained tenant turns without effect claims or pacing reservations. The worker registers only the outbound kind, with four workers and polling transport. Its forty-five-second job timeout allows the executor's thirty-second context plus detached echo, ledger and pacing writes. There is no provider callback in the leasing pool; the executor performs scoped preparation and checks authorization twice around the committed claim.

Worker outcomes follow the retained ledger:

- A delivered action or deleted source acknowledges the job. A redelivered completed job obtains no new claim.
- A running, rejected or uncertain action cancels the job. A bookkeeping failure after a claim also cancels with a fixed error; the ledger's durable fence remains authoritative even if River's acknowledgement is lost.
- An infrastructure failure before a claim returns a fixed preparation error. River allows at most three attempts. Retry scheduling is capped by the original job deadline, which the executor checks against the ledger. Retry exhaustion can leave a pending action until bounded expiry recovery; it grants no send permission.
- Pacing denial snoozes only while the action is pending. Snoozes preserve the attempt count and the original deadline. A minimum delay avoids a tight loop on stale timing; every delay is capped by that deadline. On wake-up, the executor rechecks state, authorization, deadline and pacing rather than reserving a future slot.
- Invalid arguments or an elapsed deadline cancel the job. No typed provider retry hint, quota rejection or uncertainty automatically reschedules an attempted action.

When pre-claim preparation or a pacing snooze reaches the whole-second job deadline, the worker also expires its pending ledger row before cancelling the job. This conservative bound can precede the original ledger timestamp by less than one second; neither stored deadline nor job arguments change. The detached five-second write matches tenant/action and the original deadline's Unix second, checks database time, and updates pending rows only. Missing or already-started actions gain no permission; existing claims and their completion tokens remain untouched. Failed bookkeeping returns a fixed preparation error within the existing retry bound. As with other preparation failures, storage failure can leave a pending action for bounded expiry recovery, without authorizing a send.

Only fixed diagnostics cross this boundary. Provider errors, credentials, message text and panic values do not enter the worker's error strings. The existing receipt and export allowlists remain unchanged. Source/viewer/tenant deletion continues to cascade through the action and job foreign keys.

Run `bash scripts/ci-postgres.sh` for `make verify` and both uncached race suites against disposable PostgreSQL. Worker fixtures exercise real River leasing, preparation retry/exhaustion, pacing snooze/restart, expired jobs, completed redelivery, abandoned claims and terminal/bookkeeping failures. They also exercise forged tenant context, direct private-table denial, combined memberships with and without inheritance, broad PUBLIC/kind policies, missing forced RLS, dangerous grants and mismatched schemas. Synthetic send callbacks produce fixture receipts; no provider messages are sent. Existing chat leasing and lifecycle tests run alongside them.

For rollback before activation, stop any explicitly constructed fixture/client and retain the additive role, policy and all ledger/pacing state. Do not delete claims or requeue actions to repair uncertain delivery. No production sending path changes in this unit. Local fixture results do not qualify live OAuth grants, provider roles, production throughput or cutover.

## Failure diagnosis in fixtures

[Issue #90](https://git.subcult.tv/subculture-collective/overlaid/issues/90) records a hosted restart/snooze failure on merged main `de6a449`: River's job fetch reached its ten-second timeout, then the test did not observe completion. A later green run does not establish that failure's cause. The merged pacing revision `f71131c` passed [hosted verification](https://git.subcult.tv/subculture-collective/overlaid/actions/runs/15556/jobs/28701).

The fixture's completion waiter retains its fifteen-second observation budget and now applies that context to each database query. A blocked query can no longer wait beyond that budget indefinitely. On completion or snooze-observation failure, the test logs an independent diagnostic snapshot bounded to one second. It reads activity first so a locked job table cannot hide the activity result.

The snapshot contains only pool connection/wait counts; counts of active sessions, lock waits, I/O waits and blocked sessions for the worker's own database role; and job state, attempts, error count and timing relative to the database clock. Separate success flags distinguish unavailable activity/job observations from measured zeros. No job arguments, error bodies, query text, role names, credentials, claims or provider payloads are logged. Diagnostics use the existing restricted worker pool and add no grants. The regression fixture holds a disposable job-table lock, verifies that the state query honors cancellation, and confirms that a blocked job read still reports lock counts. A three-second fixture-only unlock watchdog prevents a broken waiter from hanging that regression.

October 15 local investigation on `f71131c`: eight consecutive uncached race runs of `TestOutboundRiverPacingSnoozeAndRestart` passed. Three combined uncached race runs of `platformoutbound`, `twitchoutbound` and `tenancy` also passed with the disposable PostgreSQL container limited to one CPU and 512 MiB. These are finite synthetic observations. No River fetch/worker timeout, action deadline, pacing rule, claim or startup behavior changed. The original hosted fetch-timeout cause remains unresolved; capture the failure snapshot if it recurs before choosing a runtime fix.

The timeout recurred on PR #96 at `714ef37` in [hosted run 15576/job 28730](https://git.subcult.tv/subculture-collective/overlaid/actions/runs/15576/jobs/28730). The late snapshot read activity successfully and observed a running job at attempt one, but its job scan failed. The timing zeros in that partial snapshot are unavailable measurements; the late absence of lock waits does not rule out earlier contention.

A separate diagnostic defect is reproducible without a timeout: River stores a job with no errors as a NULL error array, so `cardinality(errors)` cannot scan into an integer. The diagnostic query now counts that absence as zero. A fresh-job regression failed before this change and passed afterward; the restart fixture also checks metadata after a real snooze. This repairs the observation, not the River fetch. Runtime deadlines and claim handling are unchanged, and #90 remains open. Fifty focused uncached race repetitions of the restart test passed locally using Go 1.26.0, matching the hosted toolchain. This finite result does not reproduce or resolve the timeout.

The next head, `836f62a`, failed [hosted run 15584/job 28743](https://git.subcult.tv/subculture-collective/overlaid/actions/runs/15584/jobs/28743) during ordinary `make verify` tests, before the race suite. This time preparation exhaustion stalled at attempt two while River's batch completer twice reached its ten-second operation timeout. The complete snapshot reported one I/O wait and no lock/blocker waits at that instant. The fixture then exceeded its five-second graceful stop budget and closed the database pool; subsequent `database is closed` messages followed that cleanup. This sequence does not establish which I/O event stalled or prove that all previous failures share a cause.

The CI fixture now uses a bounded 2 GiB tmpfs, keeping PostgreSQL's normal durability settings while separating functional deadline checks from the shared runner's block-device latency. It sets `max_wal_size=256MB` in both storage modes so frequent schema creation checkpoints sooner and leaves room for database files. This is a soft checkpoint target, not a disk limit; `fsync`, `synchronous_commit` and `full_page_writes` remain enabled. [PostgreSQL WAL configuration](https://www.postgresql.org/docs/17/wal-configuration.html) describes the checkpoint and I/O tradeoff. Select `OVERLAID_CI_POSTGRES_STORAGE=volume bash scripts/ci-postgres.sh` for a disk-backed comparison. Neither mode qualifies physical power-loss durability. Container cleanup includes its owned anonymous volumes; older runs used `docker rm -f`, leaving those volumes behind. No historical volume pruning is part of this change. Cleanup failures also fail the script instead of being silently ignored.

A finite comparison on the actual Kuznya runner used the Go 1.26.0 race binary and the hosted runner image. Five repetitions each of preparation exhaustion/expiry and pacing snooze/restart passed with disk-backed storage, and the same checks passed with tmpfs. The disk-backed observation sampled `WalSync`; these successful samples did not reproduce a ten-second stall. Both comparison fixtures verified cleanup of their own containers and anonymous volumes. The complete local Go 1.26.0 gate passed with the 2 GiB mount; sampled peak usage was about 1,238 MiB, above the rejected initial 1 GiB allocation. `fsync`, `synchronous_commit` and `full_page_writes` were all verified on. This supports isolating CI storage, while #90 remains open for the unexplained hosted operation timeouts.
