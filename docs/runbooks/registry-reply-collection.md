# Source-bound registry reply collection

Tracking: [#123](https://git.subcult.tv/subculture-collective/overlaid/issues/123), parent [#24](https://git.subcult.tv/subculture-collective/overlaid/issues/24). This is unit two of the [outbound cutover plan](../superpowers/plans/2026-10-16-outbound-registry-cutover.md).

The private `newRegistryReplyAdmission` constructor binds a tenant-scoped product database and the existing outbound store. [Explicit retained chat startup](retained-chat-sender.md) installs it before a runtime starts; legacy remains the default. This collector adds no parser or SQL migration.

When explicitly selected before a runtime accepts work, `dispatchRetainedChat` opens a private collector after the existing echo check. It reconstructs the canonical Twitch envelope, checks tenant identity and requires the exact envelope to exist in retained storage. Changed input, missing sources and foreign tenants fail before command execution. The existing processor still performs parsing, aliases, roles, plan checks, cooldown reservation and response rendering once. The existing durable dispatch receipt remains the handler replay fence.

Custom commands in `chat` or `both` mode append their actual chat response. `newsroom_current` appends the selected approved item's announcement, or the existing empty-desk reply. Overlay-only commands, empty rendered responses and denied/cooling-down commands append no reply. Ticker/alert effects, display publication, history and Newsroom editorial mutations keep their existing paths. These effects are not transactional with the outbound ledger.

The central chat-send boundary collects instead of contacting Twitch while this explicit selection is present. A callback without the current private output context fails, including dashboard/manual announcements. A stale output context, changed display action ID, repeated effect, missing saved command metadata, closed collector or cancellation cannot add another reply. Admission failure never invokes the legacy provider transport. Manual announcements require their separate source and queued-acknowledgement contract before activation; do not synthesize viewer chat events.

Each reply key hashes `registry-reply-v1`, the saved command ID, its tenant-scoped snapshot fingerprint, a versioned effect kind (`chat-response-v1` or `newsroom-current-v1`) and effect position zero. These output contracts each produce one chat effect. Random display-event IDs and rendered text are excluded from the key. The original canonical event and connection bind the action identity through the [batch admission store](reply-batch-admission.md). Repeating an identical reply returns the existing action/job; changed rendered text under the same key is an immutable conflict. Different saved configurations have different keys. The durable dispatch fence must still prevent rerunning an already-started handler.

After all synchronous output publication succeeds, the collector closes and calls [transactional registry admission](registry-admission-binding.md). Every new reply's saved snapshot and command entitlement are checked under the tenant/command locks held through the action/job commit. `AdmitRegistryBatch` retains the batch store's sixteen-reply bound, source lifecycle checks, combined plan limits and original deadline. Existing identical actions are metadata-only noops. No provider message ID or delivered receipt is returned by collection. A successful handler result means admission completed; later delivery requires the separately authorized executor.

Cancellation, publication errors or an aborted collector leave no newly admitted replies. Previously committed actions remain unchanged on duplicate/conflict failures. Source deletion after collection is checked again by admission, and normal source lifecycle cascades remove admitted actions/jobs. The collector itself stores no durable credential or additional source data.

## Verification and remaining work

The disposable PostgreSQL fixture exercises the existing custom response modes and overlay effects, Newsroom current, cooldown/role rejection, repeat dispatch identities, immutable rerender conflicts, stale snapshots, cancellation, exact retained-envelope/tenant checks, source deletion and expired admission. A failing mock transport confirms these paths make zero provider requests. Pure tests cover output ordering, duplicate/missing output identity, context ownership and display-independent keys. The full PostgreSQL verification/race gate remains required.

The collector alone is not a one-sender deployment guard. The [opt-in application controller](retained-chat-sender.md) supplies pool validation, persistent selection, effect fences, readiness and shutdown. Broader lifecycle/load and live acceptance remain unfinished. No live Twitch/OBS behavior or full thousand-channel delivery qualification is implied.
